# 🔬 `digital_born/` — Phase 0 exploration scratch space (Issue #18)

Not shipped code. Nothing here is imported by `api_util/`, and nothing here is a test.
This directory exists so the PDF/DOCX tool choices in
[`../agent_dev_logs/plans/18.plan.md`](../agent_dev_logs/plans/18.plan.md) §2 were made
against real output rather than documentation.

The converter itself lands in `api_util/digital_to_json.py` (PR 5). Everything in here is
deletable the day it does.

## 📁 What's in here

| Path                         | What it is                                                              |
|------------------------------|-------------------------------------------------------------------------|
| `probe_docling.py`           | Docling → its own IR, for both PDF and DOCX. Structure only.            |
| `probe_pdf_geometry.py`      | Per-line coordinates from either engine. **The A/B harness** — below.   |
| `probe_ooxml.py`             | `python-docx` / `docx2python` on the raw OOXML, for what Docling drops.  |
| `sample.pdf`, `sample.docx`  | Real-world exploration inputs, ~2-3 MB. **Not fixtures.**               |
| `sample.pdf_docling_ir.json` | 197 KB of real Docling output from `probe_docling.py`.                  |

Install the stack with `pip install -r ../requirements_digital.txt`. PyMuPDF is
**deliberately not in it** (see the licence section) — install it in a scratch venv only for
the duration of the A/B.

## ⚠️ The probes are not tests, and are not named as if they were

They were called `test_docling.py` / `test_pymupdf.py` / `test_ooxml.py`, and the rename to
`probe_*.py` has **landed**. Recorded because the reasoning applies to anything added here:

1. **They are not tests.** No assertions, no fixtures, no isolation. They print structures
   for a human to read. A green pytest run that includes them proves nothing.
2. **They import optional dependencies.** `requirements_digital.txt` is deliberately *not*
   in the base install, so on any machine without `docling` installed, pytest collection
   **errors at import time** — a red suite caused by a probe, not by the code under test.
3. **They read multi-megabyte fixtures.** `sample.pdf` / `sample.docx` are ~2-3 MB each.

Collection is now blocked two ways: `python_files = test_*.py` no longer matches, and
`../pytest.ini` carries

```ini
[pytest]
norecursedirs = digital_born .git build dist *.egg-info .venv venv
```

Note the syntax — an earlier revision of this file gave that snippet as
`[tool.pytest.ini_options]` with `norecursedirs = ["digital_born", …]`, which is the
**pyproject.toml** form. In `pytest.ini` the section is `[pytest]` and the value is a
whitespace-separated list; the TOML version is silently ignored, so the fallback it offered
would not have worked. `testpaths = tests` covers a bare `pytest`, but not `pytest .`, nor a
pre-commit hook passing changed files, nor most IDE "run tests in this folder" actions —
which is why `norecursedirs` is there as well.

### These are not the test fixtures

Golden tests use `tests/fixtures/digital/`, generated by
[`make_fixtures.py`](../tests/fixtures/digital/make_fixtures.py): `minimal.pdf` (1039 B),
`garbled.pdf` (722 B), `minimal.docx` (4455 B), with a `MANIFEST.json` of sha256s beside
them and a `--verify` mode that fails on drift against **both** the manifest and any bytes
on disk. `tests/test_digital_fixtures.py` runs the generator, so the pinning is enforced by
the suite rather than only advertised.

A golden `expected.json` diff over a 2-3 MB real document is unreviewable — nobody can
tell an intentional change from a regression. Over a 700-byte document where every glyph
position was chosen deliberately, it is readable in a code review. Both kinds of input have
a place; they are not interchangeable.

## ⚖️ The PyMuPDF licence A/B — run this before PR 3

**Why it matters more than a normal dependency choice.** Rule 5 of the accretion contract
merges component licences as a **most-restrictive union** into `provenance.license` on
every document record. Declaring PyMuPDF (AGPL-3.0) as a component of a `digital-convert`
run therefore sets `provenance.license = AGPL-3.0` for **every digital-born document**, and
that field is what goes to catalogue export. The blast radius is the licence on the output
data for an entire input class.

That union only works if the components are *declared*. `../para_config.txt` now carries
`[components]` rows for `docling`, `pdfplumber`, `python-docx` and `docx2python` — without
them `log_component()` records `UNKNOWN`, `para_licenses` treats `UNKNOWN` as maximally
restrictive, and a digital-born record came out with `provenance.license = "UNKNOWN"`
regardless of how permissive the real stack was. Add a library to
`../requirements_digital.txt` and to `../para_config.txt` in the same change, or this whole
section is theatre.

**Why PyMuPDF is probably avoidable.** Docling already owns structural grouping, so
PyMuPDF's unique contribution is only precise span geometry and its block API. Measured
against `tests/fixtures/digital/minimal.pdf`, pdfplumber (MIT, already vendored for the
docmd stack) returns:

```
$ python probe_pdf_geometry.py --engine pdfplumber --pdf ../tests/fixtures/digital/minimal.pdf
line-level: [72.0, 62.484, 275.436, 74.484]  Helvetica 12.0  'Excavation report, block one, line one.'
            [72.0, 76.484, 274.092, 88.484]  Helvetica 12.0  'Excavation report, block one, line two.'
            [72.0, 122.484, 256.752, 134.484] Helvetica 12.0 'Block two is a separate paragraph.'
gaps:       {"page": 1, "gaps_pt": [2.0, 34.0], "separable": true}
            -> 2.0 pt within a paragraph vs 34.0 pt between: block boundaries are
               derivable from geometry alone, without PyMuPDF's block API
```

That is every field `lines[].bbox` needs, plus the font and size data. Note the harness
emits `$defs/bbox`'s convention directly — **origin top-left, y increasing downwards, in
points** — which for pdfplumber means `top`/`bottom` and never `y0`/`y1`. Writing the
bottom-up pair into a record is the specific mistake the schema's `$defs/bbox` description
now spells out.

**The protocol.** Extract the same document with both engines, join on line text, and
record the coordinate deltas:

```bash
pip install pymupdf   # scratch venv only — do not add it to requirements_digital.txt
python digital_born/probe_pdf_geometry.py --engine pdfplumber --pdf digital_born/sample.pdf > /tmp/plumber.json
python digital_born/probe_pdf_geometry.py --engine pymupdf    --pdf digital_born/sample.pdf > /tmp/mupdf.json
python digital_born/probe_pdf_geometry.py --compare /tmp/plumber.json /tmp/mupdf.json
```

The comparison prints `max_edge_delta_pt` against a 0.5 pt threshold and a verdict, plus the
twenty worst lines and any line only one engine found. Decide on the numbers, and write the
decision into `18.plan.md` §2 either way:

* **Deltas below ~0.5 pt on a real document** → drop PyMuPDF, keep the stack permissive.
* **Deltas that actually matter** (rotated text, CID fonts, multi-column) → then the AGPL
  question is real and goes to the maintainers with evidence attached, rather than as a
  dependency someone noticed late. It goes to `../para_config.txt` in the same change.

Run it on `sample.pdf`, not on the minimal fixture — the fixture is Helvetica at one
rotation, which is exactly the easy case where the two libraries will agree. `--compare` on
two dumps from the *same* engine is a useful sanity check: it must report `0.0`.

## 🧪 `garbled.pdf` and why the decode-sanity check is not optional

Issue #10's research pass found digital-born PDFs where **every** text parser returned
plausible-looking text with systematically wrong diacritics — non-embedded WinAnsi
Helvetica with no `/ToUnicode` map. `tests/fixtures/digital/garbled.pdf` reproduces that
construction deliberately. Extraction *succeeds*:

```
intended : 'Zpráva o sondě číslo 3.  Nalezeny hřeby …  Vrstva ornice měla …'
extracted: 'Zpráva o sondì èíslo 3.  Nalezeny høeby …  Vrstva ornice mìla …'
```

Note `Zpráva` survives — `á` sits at the same codepoint in both encodings. The output is
*partially* correct, which is what makes it dangerous: no length check, no encoding error,
no exception. The only thing that catches it is a lexical quality gate.

This is why `digital-convert` is granted `pages[].needs_ocr` in `BLOCK_FIELD_OWNERS`: a
digital-born page whose text layer does not decode should be routed onward to OCR, and this
converter is the only component positioned to notice. **Born-digital ≠ trustworthy text.**

Two things about that hand-off, both now enforced rather than assumed:

* Always write `pages[].needs_ocr_reason` next to it. `needs_ocr` means the **opposite**
  thing on the two paths — "no text layer" for a scan, "a text layer that lies" here — and
  the Markdown renderer emits it as a cue the model reads. Without the reason field every
  digital-born page rendered `<!-- NEEDS_OCR: pg_N (no extractable text layer) -->`, which
  is false by definition for a document that has one.
* Setting `needs_ocr` is what **authorises** `alto-postprocess` to re-originate that
  record's positional plane. `source.origin` stays `digital-born-pdf` (it describes how the
  original was acquired, and it really was), the block stamp names whoever wrote the plane,
  and `pages[].ocr` — never granted to `digital-convert` — records that an engine ran. Until
  this was wired up, §3's "route per page before deferring to OCR" was unreachable: the
  origin check refused every write `alto-postprocess` attempted on such a record.

For the garbage lines themselves, emit `lines[].categ` of exactly `"Garbage"` or
`"Inverted"`. Those two strings are what `api_util/json_to_md.py`'s `DROP_CATEGORIES`
filters on; `categ` is an open string in the schema, so a synonym silently disables the
filter instead of failing validation.
