## Context

* Issue #18 requires bridging digital-born documents (PDF and DOCX) into the LLM semantic enrichment workflow.
* Previously (via Issue #10), the pipeline relied on a PDF/DOCX → Markdown conversion, utilizing HTML comments (`<!-- BBOX -->`, `<!-- PAGE_BREAK -->`) to preserve spatial cues.
* This strategy explicitly rejects rewriting the Markdown pipeline. Instead, we are treating Issue #18 as an **architecture-first conversion task**.
* The pipeline will transition from a paradata-pair accretion model to utilizing `atrium_document` as the first-class intermediate representation (IR). Markdown is no longer the IR.
* **What changed since the first draft:** PR 0 was never a TODO — `digital_born/probe_docling.py` and siblings already exist and had been run against `sample.pdf`, producing real Docling IR (`sample.pdf_docling_ir.json`, 197 KB). The same change relocated the legacy `api_util/*_to_md.py` converters and broke three test modules; that is §0, now fixed.
* **What changed on the second pass (2026-08-03):** implementing the §1a decision surfaced that the *stated* blocker was only part of the problem. The plan's own "landed ✅" claims needed auditing against the repo rather than trusted — see §0b in particular, where a change recorded as landed had in fact landed in one of two byte-identity-enforced copies.

## §1 — The Mapping Contract ✅ decided

* **Decision (2026-08-03)**: extend the schema rather than accept a fidelity loss. `lines[]` items gain a `group_id` field (`string | null`) — lines sharing a `group_id` are contiguous, same-reading-order, and came from the same DOCX paragraph/table row or PDF text block; `null` for OCR/ALTO lines from alto-postprocess, which stays line-only. Deliberately kept as a field on `lines` rather than a new nesting level, so `bbox` and the `entities` block's `page`/`line` keys don't have to learn a second addressing scheme.

### §1a — Block ownership for digital-born docs ✅ RESOLVED

**The question.** `BLOCK_OWNERS` hardcoded `pages`/`content`/`lines`/`tables` as owned by `alto-postprocess`, on the assumption that ALTO/OCR always originates a document's positional data first. A digital-born PDF/DOCX never runs alto-postprocess, so no `program` identity was authorized to originate them.

**The decision.** Neither of the two options originally tabled. `BLOCK_OWNERS` conflates two different things — *who is authoritative for a block's semantics* and *who happens to originate it first* — and for the positional plane those differ. The second question already has an answer in the record: **`source.origin`**, which is already first-writer-wins in `set_source()` and already carries the right examples (`digital-born-pdf`, `docx`, `ocr:pero`, `ABBYY-ALTO`).

So: **one originator *role* per block, a declared candidate tuple, and the choice fixed per document by `source.origin`.**

```python
BLOCK_OWNERS: Dict[str, Union[str, Tuple[str, ...]]] = {
    "pages":   ("alto-postprocess", "digital-convert"),
    "content": ("alto-postprocess", "digital-convert"),
    "lines":   ("alto-postprocess", "digital-convert"),
    "tables":  ("alto-postprocess", "digital-convert"),
    ...
}

ORIGIN_ORIGINATORS: Tuple[Tuple[str, str], ...] = (
    ("digital-born", "digital-convert"),
    ("docx",         "digital-convert"),
    ("ABBYY-ALTO",   "alto-postprocess"),
    ("ocr:",         "alto-postprocess"),
    ("vlm:",         "alto-postprocess"),
)
```

`_assert_origin_consistent()` enforces it, and is **self-guarding** — a no-op for single-owner blocks, for non-candidate programs (nlp-enrich merging morphology into `lines[]` is a field contribution, not an origination claim), for records with no `source` yet (rule 3), and for origins the table hasn't been taught (abstain, don't block). So it is additive for every pre-#18 caller.

It is also called from **`merge_block()`**, which previously bypassed `_assert_owner()` entirely — that is why `pages` and `lines` were never ownership-checked at all, the half of §1a the first write-up missed.

**Why the two tabled options were rejected** (recorded so this isn't relitigated):

1. **No-op alto passthrough.** Stamps `assembled.blocks[<block>].program = "alto-postprocess"` and appends a `provenance.contributors[]` entry with a `paradata_ref`, for a run that did nothing, in a record whose purpose is FAIR catalogue export. Rule 4 exists for attribution granularity; this falsifies it. It also puts the alto container back on the digital-born critical path, which the four-layer design exists to avoid.
2. **A second name in `BLOCK_OWNERS` with no further guard.** `content` and `tables` are not field-split, so either originator could `set_block()` straight over the other's. The mutual exclusivity that makes two originators safe would be an unwritten assumption instead of a check.

**Why `source.origin` and not the `assembled.blocks` stamp:** rule 4 says the stamp on a field-split block names the **most recent** writer. Once nlp-enrich merges into `lines[]`, the originator signal is gone. `source` is immutable after first write.

**No `SCHEMA_VERSION` bump.** A literal reading of `docs/document_schema.md`'s versioning rule 2 ("changing block ownership bumps to the next major") would force a `2.0` migration across five repos. It shouldn't: no field is renamed or removed, every existing record stays valid, every existing tool keeps every capability, and `BLOCK_OWNERS` is a *write-authorisation* table whose read-time counterpart (`assembled.blocks[<block>].program`) is unchanged. Rule 2 is amended to say so explicitly — **widening write authorisation is additive; re-attributing an already-written block would not be** — because leaving it implicit invites either an unnecessary migration or a silent contract break.

### §1b — 🚨 NEW: as first landed, §1 silently dropped all text and bbox

`BLOCK_FIELD_OWNERS["lines"]["llm-enrich-digital"] = ["group_id"]`. Trace `merge_block()`:

```python
allowed  = ["group_id"]
writable = {"group_id"} | {"page", "line"}
patch    = {f: v for f, v in incoming.items() if f in writable}   # ← silent
```

`text` and `bbox` are discarded **with no warning** — `_complain()` only fires when `allowed is None`, and this grant is not `None`. Then `lines.items.required` is `["page", "line"]` only with `additionalProperties: true`, so the record **passes** `jsonschema.validate()`. §2's "validation is a runtime gatekeeper" does not gate this class of defect at all.

It surfaces three stages later: `json_to_md._rows_from_lines` skips empty-text lines, `rows` comes back empty, `content` can't be written either, and you finally get `ValueError("nothing to render")` pointing at the wrong thing.

Also: **`lines[].bbox` was granted to `nlp-enrich`, not `alto-postprocess`** — so the PDF adapter, whose entire selling point per §3 is exact native coordinates, was not authorized to write the field that carries them.

Corrected grants:

```python
"pages": {
    # ... existing owners unchanged ...
    "digital-convert": ["page_index", "canvas", "quality_score", "quality_band", "needs_ocr"],
},
"lines": {
    "alto-postprocess": ["categ", "quality_score", "lang", "text"],
    "nlp-enrich": ["lemma", "upos", "feats", "teitok_ref", "bbox"],
    "digital-convert": ["text", "bbox", "group_id", "lang", "quality_score", "categ"],
},
```

`bbox` is granted twice deliberately — on the ALTO path nlp-enrich derives it while aligning to TEITOK; on the digital-born path there is no TEITOK and the adapter's native coordinates are the only bbox the record will ever have. The two never meet on one document, and that is now enforced rather than assumed.

**Two mitigations, at different scopes:**

* **Local (in scope for #18).** A round-trip assertion in Layer D, before `validate()`:

  ```python
  written = {(r["page"], r["line"]): r for r in doc.get_block("lines") or []}
  for row in rows:
      got = written.get((row["page"], row["line"]), {})
      lost = [f for f in ("text", "bbox", "group_id") if f in row and f not in got]
      if lost:
          raise RuntimeError(
              f"line {row['page']}/{row['line']}: {lost} dropped by merge_block — "
              f"{PROGRAM!r} is not declared for them in BLOCK_FIELD_OWNERS['lines']"
          )
  ```

* **Ecosystem (its own PR, not bundled here).** `merge_block()` should complain when it drops fields the caller supplied:

  ```python
  dropped = {f for r in records for f in r} - writable
  if dropped:
      self._complain(f"{self.program!r} may not write {sorted(dropped)} in block {name!r} — dropped. "
                     f"Declare them in BLOCK_FIELD_OWNERS or pass own_fields=[...]")
  ```

  This makes silent field loss impossible for all five tools and would have caught §1b immediately — but it is **not free**. At least one existing call site passes context fields it doesn't own for readability (`tests/test_atrium_document.py` has the translator merging `entities` with `surface`, which translator doesn't own), so it would start warning and would raise under `strict=True`. A deliberate tightening pass with call-site cleanup, on its own.

### §1c — 🚨 NEW: `group_id` is inert until a consumer reads it

`api_util/json_to_md.py` turns the record back into the LLM's diet. `_rows_from_lines` builds `{page_num, line_num, text}` plus an optional `bbox` and **drops everything else**; `_pages_meta` reads only `canvas`/`needs_ocr`/`ocr`. So the paragraph fidelity §1 bought never reaches the model. A schema field with no consumer is a no-op with extra steps.

The fix is smaller than expected and worth recording as a design point: **Markdown already encodes paragraphs natively as a blank line**, so a `group_id` boundary needs *no new `layout_md` cue* — it maps onto the format's own primitive rather than onto another `<!-- … -->` comment. `rows_to_layout_markdown` tracks `current_group` and appends `""` on a change; with `group_id` absent everywhere (the ALTO path) the output is byte-identical.

`tables` rendering is the remainder: the block carries grid **shape** only, so emitting it means joining `tables[].cells` back to line text through `group_id` and feeding `layout_md`'s existing `md_table` emitter. Deliberately not stubbed — a half-rendered table is worse for the model than the grouped lines it already gets.

Two smaller finds in the same file:

* `_rows_from_lines` does `int(line["page"])` and `continue`s on failure, but the schema keeps `page` a string *"so 'iv' or 'A-1' survive"*. Non-numeric page labels vanish with no diagnostic. The renderer genuinely needs an int key so the cast stays; the silence doesn't. The digital converter should emit numeric labels (natural for PDF/DOCX).
* `DROP_CATEGORIES = {"Garbage", "Inverted"}` — §2's Layer B should emit **exactly these two `categ` values** rather than inventing new ones. That reuses the existing filter and routes Issue #10's diacritic-corruption finding into the JSON path for free.

### §1d — Program identity: `llm-enrich-digital` → `digital-convert`

Every other identity in these tables is a **role** (`alto-postprocess`, `page-classification`, `nlp-enrich`), not a repo. `llm-enrich-digital` encodes the accident that this converter happens to live in `atrium-llm-enrich`, and that is not cosmetic:

* it lands in `provenance.contributors[].program` in FAIR catalogue exports — permanently;
* any consumer doing `program.startswith("llm-enrich")` conflates a pre-processing converter with the enrichment stage;
* it is simultaneously a `ParadataLogger` identity needing a `para_config.txt` component→licence mapping, so it's a two-schema commitment.

### The mapping table

| Source concept       | PDF Adapter            | DOCX Adapter            | `atrium_document` Target                                                      |
|----------------------|------------------------|-------------------------|-------------------------------------------------------------------------------|
| Document metadata    | PDF metadata           | Core properties         | `source` + document metadata                                                  |
| Page                 | PDF page               | Derived from pagination | `pages[]` item                                                                |
| Text block/paragraph | PDF text grouping      | Paragraph/table/etc.    | `lines[].group_id` (shared value across the group's lines)                    |
| Text line            | PDF positioned text    | Paragraph/run-derived   | `lines[]` item                                                                |
| Text                 | PDF text span          | DOCX run                | `lines[].text`                                                                |
| Bounding box         | Native PDF coordinates | **Omitted** (§3)        | `lines[].bbox`                                                                |
| Table grid           | Detected table         | `w:tbl`                 | `tables[]` item, cells linked to text via `group_id`                          |
| Font family / size   | PDF font               | DOCX run                | ⚠️ still homeless — not in `lines` properties. Decide in PR 1 (see below).    |
| Page break           | Page boundary          | Explicit/derived break  | `pages[]` boundary                                                            |
| Undecodable text     | no `/ToUnicode`        | n/a                     | `pages[].needs_ocr` + `lines[].categ = "Garbage"`                             |

**The font row is still open.** Three options for PR 1: (a) accept the loss — Issue #10's cue taxonomy carried `FONT` but the LLM arguably needs style, not typeface; (b) add `lines[].font` (`{family, size, bold, italic}`) as an additive field, same reasoning as `group_id`; (c) map only *semantic* style (bold/italic/heading) and drop typeface, since `categ` already carries heading-ness. Recommend **(c)** — it is what a downstream reader can act on, and pdfplumber/python-docx both supply it. Do not leave it undecided into PR 3, which is how §1 became ambiguous the first time.

## §2 — Four-Layer Architecture Design

* **Layer A — Format Extraction (`api_util/digital/`)**: **Docling** as the primary structure foundation across formats; a **PDF geometry** library for exact coordinates (see the licence decision below); **python-docx / docx2python** as OOXML fallback where Docling drops Word metadata. `pdf.py` and `docx.py` extract into a shared internal `DigitalDocument`.
* **Layer B — Layout Normalization**: normalizes coordinates, reading orders and groups; applies quality-score heuristics (vowel/consonant ratio, dictionary hit-rate, perplexity gates) to filter garbage text and inverted fonts. **Emit `categ` ∈ `{"Garbage", "Inverted"}`** so `json_to_md`'s existing `DROP_CATEGORIES` filter applies unchanged.
* **Layer C — Serialization**: converts `DigitalDocument` into a strict `AtriumDocument` dictionary via `DocumentRecord`, as `program="digital-convert"`, calling `set_source(origin="digital-born-pdf" | "docx")` **before** any block write, since that is what authorizes them (§1a).
* **Layer D — Validation & Export (`api_util/digital_to_json.py`)**: strict schema validation. **Rule:** if `jsonschema.validate()` fails, no `doc.json` is emitted. **Plus** the §1b round-trip assertion, because the schema cannot catch a field-ownership drop.

### PDF geometry: a licence decision, not just a technical one 🔴

Rule 5 merges component licences as a **most-restrictive union** into `provenance.license` on every record. Declaring **PyMuPDF (AGPL-3.0)** as a component of a `digital-convert` run sets `provenance.license = AGPL-3.0` for **every digital-born document**, and that field goes to catalogue export. The blast radius is the licence on the output data for an entire input class, not one dependency line. Issue #10's research pass already flagged PyMuPDF under "licence traps" against an otherwise permissive-first stack.

**The escape looks cheap.** Docling already owns structural grouping, so PyMuPDF's unique contribution is only precise span geometry. Measured against `tests/fixtures/digital/minimal.pdf`, **pdfplumber** (MIT, already vendored for the docmd stack) returns char-level geometry to three decimals (`x0=72.000 x1=80.004 top=62.484 bottom=74.484`), plus `fontname`, `size` and the transformation matrix, with inter-line gaps that make block boundaries detectable (2.0 pt within a paragraph vs 34.0 pt between). That is every field `lines[].bbox` needs plus the font data the mapping table wants.

**Run the A/B on `sample.pdf` before PR 3** (protocol in `digital_born/README.md`), not on the minimal fixture — the fixture is single-rotation Helvetica, exactly the easy case where the two agree. Decide on the numbers and record it in this section either way.

## §3 — Format-Specific Fidelity Rules

* **PDF (Spatial Priority)**: prioritize exact character/span coordinates, strict reading orders and native bounding boxes. Mixed PDF processing routes per page on digital-text-layer detection before deferring to OCR — expressed in the record as `pages[].needs_ocr`.
* **DOCX (Structural Priority)**: preserve paragraphs, heading styles, explicit page breaks and tables. **Do not fabricate bounding boxes** where renderer coordinates are unavailable — `lines[].bbox` is simply absent, and that is documented rather than approximated. The tension with §1 that this rule used to have is resolved: paragraphs are preserved as `lines[].group_id`, independent of geometry.
