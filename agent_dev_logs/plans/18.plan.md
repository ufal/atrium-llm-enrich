## Context

* Issue #18 requires bridging digital-born documents (PDF and DOCX) into the LLM semantic enrichment workflow.
* Previously (via Issue #10), the pipeline relied on a PDF/DOCX → Markdown conversion, utilizing HTML comments (`<!-- BBOX -->`, `<!-- PAGE_BREAK -->`) to preserve spatial cues.
* This strategy explicitly rejects rewriting the Markdown pipeline. Instead, we are treating Issue #18 as an **architecture-first conversion task**.
* The pipeline will transition from a paradata-pair accretion model to utilizing `atrium_document` as the first-class intermediate representation (IR). Markdown is no longer the IR.
* **What's changed since this plan was first drafted:** a check against the `test` branch on 2026-08-03 shows PR 0 (Phase 0 Prototyping) is not actually a TODO — `digital_born/test_docling.py`, `test_pymupdf.py`, `test_ooxml.py` exist and `test_docling.py` has been run against `sample.pdf`, producing real Docling IR output (`digital_born/sample.pdf_docling_ir.json`). ## §1 — The Mapping Contract

* Before implementing the converter, the exact mapping to `atrium_document.schema.json` must be frozen to ensure compatibility with downstream TEITOK/ALTO processors.
* **Correction from the 2026-08-03 schema check**: the schema has no intermediate paragraph/text-block grouping node. `pages` is a flat array of page-level metadata; `lines` is a flat array of line records, each carrying its own `page`, `line` index, and `bbox` (via `$defs/bbox`); `content` is doc-level reading-order text. There is no `lines`-within-`block`-within-`page` nesting.
* This also means the row below labeled "block" is a **naming collision**, not an existing target: this codebase already uses "block" to mean the schema's top-level field-owned sections (`BLOCK_FIELD_OWNERS`, `set_block()`/`merge_block()`, per Issue #13's `atrium_document.py`) — `pages`, `lines`, `entities`, `content`, `enrichment` — not a paragraph/run grouping. Phase 1 must resolve this explicitly: either DOCX paragraph and table boundaries are deliberately flattened to line-level only (an accepted, documented fidelity loss versus the DOCX structural-truth goal in §3), or the schema needs a real extension — e.g. a `paragraph_id`/`group` field on `lines` items — to carry them through.

| Source concept       | PDF Adapter            | DOCX Adapter            | `atrium_document` Target (needs Phase 1 resolution)                            |
|----------------------|------------------------|-------------------------|--------------------------------------------------------------------------------|
| Document metadata    | PDF metadata           | Core properties         | `document metadata`                                                            |
| Page                 | PDF page               | Derived from pagination | `pages[]` item                                                                 |
| Text block/paragraph | PDF text grouping      | Paragraph/table/etc.    | **No existing node — see correction above**                                    |
| Text line            | PDF positioned text    | Paragraph/run-derived   | `lines[]` item                                                                 |
| Text                 | PDF text span          | DOCX run                | `lines[].text`                                                                 |
| Bounding box         | Native PDF coordinates | Derived/estimated       | `lines[].bbox`                                                                 |
| Font family          | PDF font               | DOCX run                | style/font (needs a target field — not currently in `lines` properties either) |
| Page break           | Page boundary          | Explicit/derived break  | `pages[]` boundary                                                             |

## §2 — Four-Layer Architecture Design

* The implementation must enforce a strict separation of concerns to avoid duplicated JSON logic:
* **Layer A — Format Extraction (`api_util/digital/`)**:
  * Integrates **Docling** as the primary foundation for structure across formats.
  * Integrates **PyMuPDF** to extract exact PDF geometry (text blocks, coordinates).
  * Uses **python-docx / docx2python** (native OOXML) as a fallback if Docling drops Word-specific metadata.
  * `pdf.py` and `docx.py` extract this native data into a shared, internal Python model (`DigitalDocument`).
* **Layer B — Layout Normalization**: Normalizes coordinates, reading orders, and blocks. It actively applies quality score heuristics (vowel-to-consonant ratios, perplexity gates) to filter garbage text/inverted fonts.
* **Layer C — Serialization**: Converts the internal `DigitalDocument` into a strict `AtriumDocument` JSON dictionary.
* **Layer D — Validation & Export (`api_util/digital_to_json.py`)**: Runs strict schema validation. **Rule:** If `jsonschema.validate()` fails, no `doc.json` is emitted.

## §3 — Format-Specific Fidelity Rules

* **PDF (Spatial Priority)**: PDFs are inherently positioned. The adapter must prioritize text extraction, exact character/span coordinates, strict reading orders, and native bounding boxes. Mixed PDF processing must route documents based on per-page digital text layer detection before deferring to OCR.
* **DOCX (Structural Priority)**: DOCX is structurally rich but depends on renderer pagination. The adapter must preserve paragraphs, heading styles, explicit page breaks, and tables. **Do not fabricate bounding boxes** for DOCX if exact renderer coordinates are unavailable. This rule is now in direct tension with the §1 correction — there's currently nowhere in the schema to actually preserve a paragraph boundary distinct from a line boundary, so "preserve paragraphs" needs Phase 1 to land a schema decision first, not just adapter code.

## §5 — Testing & CI/CD Strategy

* Integration with centralized GitHub Actions is mandatory.
* **Unit Fixtures**: Create minimal, deterministic synthetic `.pdf` and `.docx` fixtures in `tests/fixtures/digital/` (note: `digital_born/sample.pdf` and `sample.docx` already exist as exploration fixtures but are not in `tests/fixtures/` and are not minimal/synthetic — real-world-sized files, ~2-3MB each).
* **Golden Tests**: Compare `actual.json` vs `expected.json` (with unstable metadata fields stripped).
* **Pipeline Compatibility**: Pass the generated JSON directly into the LLM semantic enrichment module (`llm_run.py`) in CI to guarantee zero downstream schema or structural panics.
* **Immediate priority**: restore green CI on `tests/test_pdf_to_md.py`, `tests/test_docx_to_md.py`, `tests/test_doc_to_visual_md.py` per §0 before adding any new test scaffolding.
