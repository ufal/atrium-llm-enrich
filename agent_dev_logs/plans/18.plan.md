# Strategy — `ufal/atrium-llm-enrich` (Issue #18: Build explicit PDF/DOCX-2-JSON converter - digital-born documents)

> Issue [\#18](https://github.com/ufal/atrium-llm-enrich/issues/18) ("Build explicit `PDF`/`DOCX`-2-`JSON` converter - digital-born documents") · Labels: `enhancement`, `development`, `integration` 
> **Status: 🧭 Architecture defined — `atrium_document.schema.json` is the sole canonical target. PDF and DOCX utilize distinct extraction adapters feeding a unified JSON serializer. Markdown is deprecated as an intermediate layer.**

## Context

* Issue #18 requires bridging digital-born documents (PDF and DOCX) into the LLM semantic enrichment workflow. 
* Previously (via Issue #10), the pipeline relied on a PDF/DOCX → Markdown conversion, utilizing HTML comments (`<!-- BBOX -->`, `<!-- PAGE_BREAK -->`) to preserve spatial cues.
* This strategy explicitly rejects rewriting the Markdown pipeline. Instead, we are treating Issue #18 as an **architecture-first conversion task**. 
* The pipeline will transition from a paradata-pair accretion model to utilizing `atrium_document` as the first-class intermediate representation (IR). Markdown is no longer the IR.

## §1 — The Mapping Contract

* Before implementing the converter, the exact mapping to `atrium_document.schema.json` must be frozen to ensure compatibility with downstream TEITOK/ALTO processors. 

| Source concept    | PDF Adapter            | DOCX Adapter            | `atrium_document` Target |
|-------------------|------------------------|-------------------------|--------------------------|
| Document metadata | PDF metadata           | Core properties         | `document metadata`      |
| Page              | PDF page               | Derived from pagination | `page node`              |
| Text block        | PDF text grouping      | Paragraph/table/etc.    | `block`                  |
| Text line         | PDF positioned text    | Paragraph/run-derived   | `line`                   |
| Text              | PDF text span          | DOCX run                | `text content`           |
| Bounding box      | Native PDF coordinates | Derived/estimated       | `bbox`                   |
| Font family       | PDF font               | DOCX run                | `style/font`             |
| Page break        | Page boundary          | Explicit/derived break  | `page boundary`          |

## §2 — Four-Layer Architecture Design

* The implementation must enforce a strict separation of concerns to avoid duplicated JSON logic:
* **Layer A — Format Extraction (`api_util/digital/`)**: 
  * Integrates **Docling** as the primary foundation for structure across formats. 
  * Integrates **PyMuPDF** to extract exact PDF geometry (text blocks, coordinates). 
  * Uses **python-docx / docx2python** (native OOXML) as a fallback if Docling drops Word-specific metadata.
  * `pdf.py` and `docx.py` extract this native data into a shared, internal Python model (`DigitalDocument`).
* **Layer B — Layout Normalization**: Normalizes coordinates, reading orders, and blocks. It actively applies quality score heuristics (vowel-to-consonant ratios, perplexity gates) to filter garbage text/inverted fonts.
* **Layer C — Serialization**: Converts the internal `DigitalDocument` into a strict `AtriumDocument` JSON dictionary.
* **Layer D — Validation & Export (`api_util/digital_to_json.py`)**: Runs strict schema validation. **Rule:** If `jsonschema.validate()` fails, no `doc.json` is emitted. 

## §3 — Format-Specific Fidelity Rules

* **PDF (Spatial Priority)**: PDFs are inherently positioned. The adapter must prioritize text extraction, exact character/span coordinates, strict reading orders, and native bounding boxes. Mixed PDF processing must route documents based on per-page digital text layer detection before deferring to OCR.
* **DOCX (Structural Priority)**: DOCX is structurally rich but depends on renderer pagination. The adapter must preserve paragraphs, heading styles, explicit page breaks, and tables. **Do not fabricate bounding boxes** for DOCX if exact renderer coordinates are unavailable. 

## §4 — Implementation and PR Rollout Sequence

* Avoid merging this as a single monolithic pull request. Decompose into an 8-step sequence:
* **PR 0 (Prototyping)**: Try out PyMuPDF and Docling tools (create scripts for that) + OOXML exploration (create scripts for that).
* **PR 1 (Contract)**: Schema audit and Source→AtriumDocument mapping tests.
* **PR 2 (Model)**: `DigitalDocument` common internal normalized representation.
* **PR 3 (PDF Adapter)**: Digital-born PDF extraction logic (Docling + PyMuPDF).
* **PR 4 (DOCX Adapter)**: DOCX structural extraction logic (Docling + OOXML fallback).
* **PR 5 (Entrypoint)**: `api_util/digital_to_json.py` + CLI auto-detection.
* **PR 6 (Integration)**: `atrium-llm-enrich` compatibility pipeline tests.
* **PR 7 (Migration)**: Deprecate `api_util/pdf_to_md.py` and `api_util/docx_to_md.py`.

## §5 — Testing & CI/CD Strategy

* Integration with centralized GitHub Actions is mandatory.
* **Unit Fixtures**: Create minimal, deterministic synthetic `.pdf` and `.docx` fixtures in `tests/fixtures/digital/`.
* **Golden Tests**: Compare `actual.json` vs `expected.json` (with unstable metadata fields stripped).
* **Pipeline Compatibility**: Pass the generated JSON directly into the LLM semantic enrichment module (`llm_run.py`) in CI to guarantee zero downstream schema or structural panics.

## Verification (Definition of Done)
* **Architecture**: PDF and DOCX use separate adapters but share a single JSON construction layer. Markdown is no longer in the conversion loop.
* **Data Integrity**: Output passes the canonical JSON schema. PDF bounding boxes are exact; DOCX bounding boxes are explicitly documented as derived/omitted. 
* **Pipeline**: CI tests prove the resulting JSON is successfully ingested by `atrium-llm-enrich` without failure.
* **Migration**: Old Issue #10 Markdown converters are regression-tested against the new JSON baseline and officially marked as legacy.
