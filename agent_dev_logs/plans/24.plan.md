## Context
The issue's own content is thin: a link to a blog post about olmOCR and a one-line note that it
"sounds interesting." Taken alone that's not actionable. Taken alongside this repo's existing
research, it isn't a new lead at all — **olmOCR is already named** in `agent_dev_logs/plans/10.plan.md`
§2c as one of the OOTB VLM transcriber candidates earmarked for the hub's **#22**
document-understanding benchmark. The right move is not a from-scratch olmOCR investigation; it's
closing the gap between this issue and the plan that already lists it.

## Strategic actions

### A — Close the loop back to `plans/10.plan.md` §2c (cheap, no research needed)
Add a cross-reference from #10's plan (or its digest) to this issue, and from this issue's digest
back to §2c — done in [`../digests/24.digest.md`](../digests/24.digest.md). Prevents a second,
independent olmOCR mention resurfacing later as if the first one never happened, the same failure
mode this session's audit has already found and fixed elsewhere in this ecosystem's dev logs
(duplicated tracking under two different issue numbers).

### B — Decide which seam olmOCR is actually being proposed for
Before doing anything with the model itself, get a one-line answer (from @K4TEL, who opened both
this issue and holds the #10 plan) on scope:
1. **Hub #22's VLM benchmark tier** — olmOCR competes against CHURRO-3B, Qwen2.5-VL, SmolDocling-256M,
   dots.ocr, DeepSeek-OCR on document-understanding quality (CER/WER/entity-F1/TEDS) via the
   existing harness. This is where §2c already placed it.
2. **#10's render+OCR path** — olmOCR competes against Tesseract `ces` (landed) and PERO-OCR
   (next candidate) as the OCR *engine* for scanned/curve-only PDF pages specifically.
These aren't mutually exclusive, but they're different comparisons with different harnesses and
different "done" criteria — conflating them risks a half-finished benchmark that answers neither
question cleanly.

### C — If (1): let hub #22 absorb it, don't run a parallel evaluation here
Hub #22 is still at "propose a concrete first step," not "execute it" — see that issue's own
digest. Running an olmOCR-specific comparison in this repo ahead of hub #22's own methodology
would duplicate effort the moment #22 executes. Wait for #22's first concrete benchmark run and
make sure olmOCR is in the candidate set it actually tests, rather than standing up a separate
evaluation here.

### D — If (2): benchmark olmOCR against Tesseract/PERO-OCR directly, using this repo's fixtures
`digital_born/probe_pdf_geometry.py`-style harnesses and the `curves.pdf`/`scan.pdf` fixtures from
§5-6 of `plans/10.plan.md` already exist for exactly this comparison shape. Reuse them rather than
building new fixtures; score with the same CER/WER pipeline `eval_metrics.py` already provides.

### E — License check, either way
Before any real run: verify olmOCR's weight license against §2's "permissive-first" bar the way
§2c requires for the whole VLM list. (olmOCR is Apache-2.0 per its own release, per §2c's note —
worth confirming against the actual model card rather than carrying the label forward unchecked.)

## Verification / done-criteria
- This issue and `plans/10.plan.md` §2c cross-reference each other (done via the digest).
- An explicit statement of which seam (hub #22 VLM tier vs. #10 render+OCR path) olmOCR is being
  evaluated for, from whoever opened this issue.
- If pursued: one benchmark run (CER/WER/entity-F1) with olmOCR in the candidate set, on either
  the hub #22 sample or the #10 `curves.pdf`/`scan.pdf` fixtures depending on which seam is chosen.

## Out of scope
- Standing up olmOCR as a production OCR path before any comparison — no candidate at either seam
  has been promoted to production based on measurement yet, and this issue's own content gives no
  reason to fast-track this one ahead of the others already on the list.
- Re-running the full VLM survey — `plans/10.plan.md` §2c and hub `#22.plan.md` already did that;
  this plan only closes the gap for the one name this issue re-raised.
