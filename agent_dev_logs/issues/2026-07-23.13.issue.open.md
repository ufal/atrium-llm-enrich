## Strategy: the three intermediate formats as a system - draft to work with

Synthesising #10 (ingestion → annotated Markdown, implemented) and #11 (Markdown is the LLM diet, decided) into a standing contract, and specifying the two open items: **the level of detail in the HTML fragments** and **the JSON schema template**.

### §A — Three planes, one job per format

Each format is authoritative for exactly one concern; nothing is asked to serve two masters. The planes are bound together by paradata provenance (`run_id`) and by explicit cross-links.

| Plane | Format | Role | Authority | Produced by |
|---|---|---|---|---|
| **Reading** | **Annotated Markdown** (`# doc` + `## Page N` + `<!-- cues -->`) | LLM input ("diet") | **Derived & disposable** — regenerable any time | `pdf_to_md`/`docx_to_md` · `xml_to_md --format layout` |
| **Layout / preservation** | **TEITOK.XML** (TEI + facsimile + bbox) | Human view, CQP/XPath search, correction, archival | **Spatial source of truth** — word/line coords + linguistic annotation | `teitok_alto.write_teitok_merged` (nlp-enrich) |
| **Search / knowledge** | **JSON** (§C template) | Text + metadata + entities + enrichment for indexing / catalogue export | **Canonical semantic record** — what search & ARIADNE/GoTriple consume | `run_document_level` (+ NER/quality merge) |
| *(invariant)* | **paradata JSON** (`atrium_paradata` v2.0) | Provenance / license / run binding | **Immutable audit trail** | every stage |

**Directionality (never circular).** Markdown is always regenerable and never the thing we preserve; **TEITOK and JSON are the two persisted artifacts**, cross-linked and both bound to the ALTO original by `run_id`:

```
ABBYY ALTO ─┐
 OCR/VLM   ─┼─► TEITOK.XML ──(xml_to_md --format layout)──► annotated MD ──► LLM ──► JSON (§C)
PDF/DOCX  ──┘      ▲ spatial truth           reading plane                   │ knowledge plane
                   └─────────── deterministic re-projection (JSON → TEITOK <name>/notes) ◄─┘
 every stage ─► atrium_paradata  (run_id binds ALTO ↔ MD ↔ JSON ↔ TEITOK; license union)
```

This is the four-phase flow from ufal/atrium-project#22 (Ingest → Markdown → JSON → TEITOK) stated as a contract, corrected to reality: the quality score is a **post-extraction per-line** signal (not a pre-extraction router), and the JSON→TEITOK re-projection **already exists** (`teitok_alto.py`).

### §B — Level of detail in the HTML fragments: **full `CUE_SCHEMA` by default**

The Markdown plane is a *derived, throwaway* view whose only job is to hand the model the richest faithful picture of the page. So the default emits **every** layout cue we can recover, as inert HTML comments a renderer hides and the LLM reads as positional hints. 

| Group | Cue | Emitted form | Default (full) |
|---|---|---|---|
| Macro-structure | `PAGE_BREAK` | `<!-- PAGE_BREAK: pg_12 -->` | ✅ |
| | `DOC_META` | `<!-- DOC_META: size=612x792pt, orientation=portrait -->` | ✅ |
| | `LAYOUT_COLUMN` | `<!-- LAYOUT_COLUMN: 1_of_2 -->` | ⚠️ reserved → to implement |
| | `STYLE` | `<!-- STYLE: color=#FF0000, highlight=yellow, line-spacing=1.5 -->` | ✅ (color/highlight; **line-spacing** reserved) |
| Document regions | `HEADER_START/END`, `FOOTER_START/END` | `<!-- HEADER_START --> … <!-- HEADER_END -->` | ✅ |
| | `WATERMARK` | `<!-- WATERMARK: "CONFIDENTIAL DRAFT" -->` | ⚠️ reserved → to implement |
| Pipeline signals | `NEEDS_OCR`, `OCR` | `<!-- NEEDS_OCR: pg_3 (…) -->` · `<!-- OCR: engine=tesseract, lang=ces -->` | ✅ |
| Inline (GFM, not comments) | bold/italic/strike/underline, `<div align>`, `![img]`+BBOX, `[^n]` footnotes, GFM tables | native GFM | ✅ all |

**Cues are positional hints, never content** — the document system prompt already tells the model to read cues for position but "never extract or quote them as content." Full detail must not change what counts as text.

**Selectable down-profiles** (a `--detail` knob over the same `CUE_SCHEMA`, kept available, not the default):
- **`standard`** — drop typography (`FONT`/`STYLE`/`LAYOUT_MARGIN`/`INDENT`/`WATERMARK`); keep structure + `BBOX` + `DOC_META` + header/footer + columns.
- **`minimal`** — structure only: page breaks, headings, GFM tables, lists, footnotes, image placeholders, `NEEDS_OCR`/`OCR`. Guarantees page-citation + reading order at near-zero overhead.

### §C — JSON schema template (the search/knowledge plane)

**Principle: harmonise, don't invent.** The template is the union of what already exists — `build_document_schema` fields, the on-disk `*_enriched.json` records, the paradata provenance block, the CNEC/OntoNotes/TEATER taxonomies, the quality bands, and the TEITOK/ALTO spatial refs — as one canonical, versioned, **FAIR** document record (stable `doc_id`, controlled vocab, ontology cross-refs, cross-walk to sibling formats).

Top-level object **`AtriumDocument`** (illustrative; *optional* layers may be externalised by reference):


**Field lineage (why each block exists / where it comes from today):**
- `schema_version` — mirrors paradata's `SCHEMA_VERSION` policy (`docs/paradata-schema.md`): additive fields need no bump; renames/semantics bump the version + ship a `_migrate_X_to_Y()`.
- `source` / `representations` — the **FAIR cross-walk**: the *same object* addressable in every plane (MD/TEITOK/ALTO/image). `origin` records treatment (`ABBYY-ALTO` | `digital-born-pdf` | `docx` | `ocr:tesseract-ces` | `ocr:pero` | `vlm:glm-4v`).
- `provenance` — **references** the paradata record (no duplication); carries the effective license so the JSON is self-describing for catalogue export.
- `pages[]` — `quality_score`/`quality_band` from `compute_quality_score` (Trash `<0.55` / Noisy `[0.55,0.80)` / Clear `≥0.80`); `canvas` from `DOC_META`; `ocr`/`needs_ocr` from the OCR cues; `teitok_surface` links into the facsimile.
- `content` — full text or a pointer to the annotated MD; keeps the JSON a usable search document without inlining megabytes.
- `lines[]` *(optional)* — mirrors nlp-enrich's CSV columns (`page/line/categ/quality_score/text`) and TEITOK `<s>`/`<lb>`; `teitok_ref` is the join back to spatial truth.
- `entities[]` — normalised NER carrying **all three tagsets** (`type_onto` OntoNotes = default configured, `type_cnec` fine legacy, `type_teitok` coarse), the LLM `translation_en`, and a nullable `pid` block for **FAIR ontology cross-refs** (Wikidata/GeoNames/AAT/AMCR) — the ARIADNE/GoTriple hook.
- `enrichment` — a superset of `build_document_schema.DocumentEnrichment` (`locator`, `page`, `extracted_keywords_cs/en`, `teater_category`, `confidence_score`) + the explicit `citation` anchor (#11), optional `summary`/`topics`, and `page_categories` from ufal/atrium-page-classification.

**Versioning & validation.** Ship alongside the template a JSON-Schema (draft 2020-12) file `atrium_document.schema.json` for CI validation, generated from a pydantic `AtriumDocument` that extends `build_document_schema` (one generator, no drift). *Where the file lives* — single-sourced/hub-canonical like `atrium_paradata.py` vs owned by llm-enrich — is **deferred**; specified here for now.

### §D — What #13 exposes (flagged, not undertaken — this is a design issue)

1. **The Markdown plane exists in only one repo.** `layout_md`/`xml_to_md`/`doc_to_visual_md` live in llm-enrich; **nlp-enrich still feeds its LLM plain CSV lines / `.teitok.xml`**, and the LLM engine (`llm_utils`/`vocab_manager`/`llm_run`) is duplicated & diverging across the two, outside `para-drift`. Unifying nlp-enrich onto annotated-MD input is the biggest downstream consequence.
2. **TEITOK correctness items** (for "TEITOK.XML for *correct* layout"): reconcile `xmlnsoff=`/`lang=` vs `xmlns=`/`xml:lang=`; make `<name>` closing tags consistent (or always run `fix_name_close_tags`); replace the hard-coded `<div type="MarginTextZone-P">` with the real ALTO block role.
3. **Provenance already the right shape** — no new format needed; `provenance` references the existing paradata `run_id`, and `merge_run_paradata.intermediate_formats` already enumerates the formats a run touched.

### §E — Deferred (kept out so this issue stays a decision, not a build)
- Reserved-cue emitters + the `--detail` knob (§B).
- The `atrium_document.schema.json` file + pydantic generator, and its distribution decision (§C).
- Unifying nlp-enrich onto MD input / de-duplicating the LLM engine (§D.1).
- The #22 token-cost bake-off (per-tier default) and the FAIR roadmap/index navigation layer (tracked under #11/#22).

---

**TL;DR** — Three planes, one job each: **annotated Markdown** (derived, disposable LLM diet, profiles to downshift) · **TEITOK.XML** (spatial source of truth + human/CQP view) · **JSON `AtriumDocument`** (canonical FAIR search record, harmonising the existing enrichment/paradata/entity schemas). TEITOK + JSON are persisted and cross-linked; Markdown regenerates from TEITOK; paradata `run_id` binds all four.

## By Opus ultracode:

### 1. The aggregate is a *derived view*, not a monolith — no forced full runs

Reframing `AtriumDocument` so it **can't** couple the pipeline:

- **Per-stage outputs stay the source of truth** and are produced/updated independently — exactly the per-stage-container model of #18. Each stage keeps writing its own persistent output (classification result · alto categ/quality · translated XML · **TEITOK** · `enriched.json`) + its own paradata. Nothing forces a full run.
- **The aggregate is assembled by a deterministic merger** — the *same* pattern `atrium_paradata.merge_run_paradata` already uses to fold per-stage paradata into one summary ("reflect EXECUTED stages only"). It *references* the per-stage slices; it doesn't replace them.
- **Incremental updates are cheap.** Each block carries the `run_id` of the stage that produced it:

  ```json
  "assembled": {
    "mode": "view",
    "source_run_ids": { "pages": "260724-071648", "entities": "260724-090012",
                        "enrichment": "260724-101112" }
  }
  ```

  Re-run one stage → only its block is re-merged (a read+copy, no LLM/NER/OCR recompute). Updating a part needs that one stage + a near-instant re-merge, **never** a full pipeline run.
- **Two materialisations, your call per production need:** `mode:"view"` — the API/service layer assembles it lazily at query time, nothing extra persisted, zero staleness; or `mode:"cache"` — a materialised `…document.json` whose staleness is detectable by comparing block `run_id`s to the latest per-stage paradata. My lean is `view` for search/presentation, `cache` only if a consumer needs a frozen artifact.

### 2. No image/thumbnail references — persistent artifacts only

Fully agree. Dropped `representations.images` and `pages[].image`. References are now restricted to the two persistent classes you name — the **original input** and **persistent step outputs**:

```json
"source":        { "filename": "CTX000000001.alto.xml", "origin": "ABBYY-ALTO", "…": "…" },
"derived_from":  {                       // ONLY persistent step outputs
  "classification": "CATEG/CTX000000001.categories.json",
  "alto_categ":     "DOC_LINE_CATEG/CTX000000001.csv",
  "translated_xml": "TRANSLATED/CTX000000001.alto.xml",
  "teitok":         "TEITOK/CTX000000001.teitok.xml",
  "enriched":       "KW_PER_DOC_LLM/CTX000000001_enriched.json",
  "paradata":       "paradata/260724-101112_pipeline-run.json"
},
"regenerable":   {                       // disposable — a recipe, not a stored path
  "markdown": { "from": "TEITOK/CTX000000001.teitok.xml", "converter": "xml_to_md@0.3.0", "detail": "full" }
}
```

- The Markdown gets the same treatment as the thumbnails: since it's *derived & disposable*, it's referenced as a **regenerable recipe** (source + converter + detail profile), not a stored path. Same principle for both — reference persistent sources + recipes, never transient derivatives.
- **Visual overlay still works without stored images:** bboxes stay in ALTO/TEITOK coordinate space; the presentation layer re-renders a page image on demand and overlays via TEITOK's `<surface>` facsimile ids. `pages[].teitok_surface` is a logical id, not an image path — so the late/transient thumbnails you mention are never referenced from here.

Net effect: the pipeline stays fully stage-by-stage and incremental, and the JSON only ever points at things that actually persist. I'll fold this into the strategy draft as a revision.

## By Opus ultracode: 

### The aggregate is produced by a dedicated service — `atrium-aggregate`

A sixth tool in the exact same mold as the five (`GET /info`, `GET /health`, one domain endpoint, zero-dependency client, Agent-Skill wrapper, `atrium_paradata` + license union). It is a **stateless pure function**: given one document's persistent artifacts, it returns that document's `AtriumDocument`. No shared state, no shared-volume assumption, no coupling back into the pipeline — matching the settled "no central orchestrator; containers reached via API" stance (ufal/atrium-project#18).

### `POST /aggregate` — given the persistent inputs, returns the JSON

```
POST /aggregate            (multipart, or a manifest of refs the caller already holds)
  doc_id          (required)
  source          original file OR { filename, media_type, sha256, origin }   (required)
  classification  CATEG/<doc>.categories.json        (optional)
  alto_categ      DOC_LINE_CATEG/<doc>.csv           (optional)
  translated_xml  TRANSLATED/<doc>.xml               (optional)
  teitok          TEITOK/<doc>.teitok.xml            (optional)
  enriched        <doc>_enriched.json                (optional)
  paradata[]      each stage's *_paradata.json       (optional, ≥1 recommended)
  params: mode=view|cache · detail=full|standard|minimal

→ 200  AtriumDocument JSON  (+ the aggregator's own paradata for this merge)
   422 unusable input · 413 too large · 503 warming (retry)
```

Only the **persistent** artifacts David listed go in — originals + persistent step outputs. No page images/thumbnails; the Markdown is not passed either (it's the `regenerable` recipe).

#### How it merges
The generalized `merge_run_paradata` discipline already shipped in `atrium_paradata`: parse each supplied artifact, project it into its `AtriumDocument` block, stamp `assembled.source_run_ids[block]` from **that artifact's own** paradata `run_id`, resolve the license union across the supplied paradata, emit. A **missing artifact simply omits/nulls its block**, and `assembled` records what was present — "reflect SUPPLIED artifacts only", the same convention as the paradata merger. It generalizes the manifest we already have (`nlp-enrich/api_util/build_manifest_row.py`).

#### Who feeds it (given there's no orchestrator)
Whoever drives the pipeline is the caller: each tool already returns its output to *its* caller over the API; that caller accumulates the set for a `doc_id` and POSTs it to `/aggregate`. In practice the **presentation/ingest layer** (which already gathers a document's persistent outputs to display) or a **post-run batch job** / the compose smoke. The aggregator never reaches into anyone's filesystem — it only ever sees what it's handed.

#### Incrementality falls out for free
Because it's stateless: "update one part" = re-POST with the one changed artifact swapped in. `mode:"cache"` consumers compare `source_run_ids` against the latest per-stage paradata and skip if unchanged. No full run, no shared state — which resolves the earlier coupling worry at the tooling level, not just on paper.

#### Placement
New `atrium-aggregate` repo/container (recommended) over an endpoint bolted onto llm-enrich — the latter would force the last stage to ingest classification/translator/TEITOK artifacts it otherwise never touches. This also settles the open "where does the schema live" question: the `AtriumDocument` pydantic model + `atrium_document.schema.json` **live in this repo** (promotable to hub-canonical later, like `atrium_paradata.py`).

### Two consistency fixes to the draft `AtriumDocument`, prompted by the persistence rule
1. **Drop `content.markdown_ref`.** It still pointed at a stored `MD/<doc>.md` path — exactly the transient-derivative reference we agreed to avoid. The Markdown is reachable via `regenerable.markdown` (source + converter + `detail`); `content.text` (inline or externalized-by-reference) is the searchable text.
2. **Reference `source` by `doc_id` + `sha256`, not a path** — originals are archive-managed, not pipeline-local; the durable key is the id + hash, with `filename`/`media_type`/`origin` as metadata.

Net: the three planes stand, the aggregate becomes a real, callable, stateless service fed only persistent inputs, and nothing references a transient artifact.

Opus 5 ultracode follow-up: adopting the paradata-pair model — it's the better design, and it turns out the machinery is already there.

`atrium_paradata.py` already implements exactly this round-trip: `_to_state_dict()` / `_from_state_dict()` (lines 234/250) serialise and restore a record mid-flight, `load_paradata()` migrates and refuses a newer major version (290–300), and `merge_run_paradata()` (364) is the fold that only ever "reflect[s] EXECUTED stages only". And there are already ~17 `ParadataLogger` construction sites across the five tools (`translator/main.py:302`, `nlp-enrich/llm_run.py:327`, alto's seven stage scripts, `llm-enrich/openrouter_client.py:249`, `page-classification/run.py:1077`, …) — those *are* the seams the paired JSON hook attaches to. So this isn't a new mechanism, it's the sibling of one that's already shipped and `para-drift`(GHA)-enforced. It also deletes a whole repo/container/service from the design and keeps every tool independently runnable, which the aggregator did not.

**The contract**, six rules:

1. Optional `--document-json` in, `--document-json-out` out (services: an optional `document_json` part in/out).
2. **A tool writes its own block only** — every other block passes through byte-identical. That invariant is what makes the pair safe.
3. **No baseline → own part only** (plus `doc_id`/`schema_version`, and `source` if it's the first writer). Standalone runs and backward compatibility, as you specified.
4. Each block is stamped with the writing tool's `program` + paradata `run_id` + `paradata_ref` (`assembled.blocks{}`) — that's where the granularity comes from.
5. License accretion via `para_licenses.merge_effective_licenses` — same most-restrictive union as paradata, so the JSON stays self-describing for catalogue export.
6. Unknown/newer blocks preserved untouched; higher major version refused by the same guard as `load_paradata`.

Re-running one tool against the current JSON therefore rewrites exactly one block — no full run, no shared-volume assumption, no tool needing to see another's outputs.

**Ownership** (one owner per block; where two tools touch `lines[]` it splits *by field*, so nothing is co-mutated):

| Tool | Owns |
|---|---|
| page-classification | `enrichment.page_categories` |
| alto-postprocess | `pages[]` quality score/band · `lines[]` *categ, quality_score* |
| translator | `translations` · `entities[].translation_en` |
| nlp-enrich | `entities[]` · `lines[]` *morphology, teitok_ref* · `derived_from.teitok` |
| llm-enrich | `enrichment.items[]` · `regenerable.markdown` |

**Placement:** `atrium_document.py` + `atrium_document.schema.json` as **hub-canonical shared** files (`docs/templates/shared/`), byte-identical in all five repos under `para-drift` — same distribution as `atrium_paradata.py`. That closes the earlier open question about where the schema lives.

## E2E-related update: the `--document-json`/`--document-json-out` CLI shape is now converged across all five tools, and two real accretion bugs are fixed - report by Sonnet

This lands the CLI-convergence and bug-fixing side of #13 that the hub's `e2e-pipeline-smoke.yml` rewrite (see [atrium-project#18](https://github.com/ufal/atrium-project/issues/18)) needed to actually work end to end, rather than just structurally thread a document JSON through five stages that couldn't really read/write it yet.

### 1. File-pair flags added to the three directory-only tools

`page-classification` and `translator` already supported the single-file `--document-json`/`--document-json-out` pair; `alto-postprocess`, `nlp-enrich`, and `llm-enrich` supported only the directory form (`--document-json-dir`). All three now support both, via the same pattern: seed a scratch `--document-json-dir` from the single-file baseline, let the existing (already-correct) directory-form accretion do its job, then copy the one output file back out to the caller's exact path.

- **`atrium-alto-postprocess/run_pipeline.py`** — `--document-json`/`--document-json-out` were already declared in argparse but never read anywhere else in the script; every stage script (`page_split.py`, `extract_*.py`, `classify_TEXT.py`, `aggregate_STAT.py`) only ever honored `--document-json-dir`/`DOCUMENT_JSON_DIR`. Wired as a thin wrapper around that existing, working mechanism.
- **`atrium-nlp-enrich/run_pipeline.py`** — added the same flag pair, wrapping the "stats" stage's existing `--document-json-dir` support (the only stage that touches the document record).
- **`atrium-llm-enrich/openrouter_client.py`** — added the same flag pair (single-file scope: `--input` must be one file, not a directory).

### 2. `nlp-enrich`'s entity extraction had never actually run against real data

Independent of the CLI wiring, `api_util/document_hook.py`'s `run_document_hook()` was completely non-functional the moment it saw a non-empty CoNLL-U file:

- It called `parse_and_align_conllu(conllu_path)` **without** `alto_path`, so ALTO bbox alignment never happened, and it treated the function's return value (a dict keyed by `"sentences"`, `"alto_strings"`, etc.) as if it were a flat token list.
- `group_ner_spans()` groups **every** token (tagging each span `"name"` or `"plain"`) and gives name spans a raw NER `"code"`, not a `"type"` key — the code read `span["type"]`, which never existed.
- `char_span` was hardcoded `None`.
- `is_cnec` tagset detection read a `"misc"` key tokens never carried (only `"ner"`).

The combination produced a guaranteed `KeyError: 0` on any real input — silently swallowed by `summarize_nt_udp.py`'s broad `except Exception`, so the `entities[]` block was just never populated in production, with only a warning printed to stderr. This is exactly the kind of "green but broken" failure the whole #18 CI-hardening effort has been chasing.

**Fix, reconciled with an independent fix already on `atrium-nlp-enrich`'s `test` branch** (found mid-session — same root causes, arrived at independently): flatten `parsed["sentences"]` before use, thread `alto_path` through from `summarize_nt_udp.py`'s existing `alto_dir`, filter to `kind == "name"` spans, derive `is_cnec` from span codes against `CNEC_TO_CONLL`, and compute a real `char_span` via a running character cursor across tokens in document order (not a substring search, which can misplace a repeated surface string within its line). Also switched `entities[]` from `set_block` to `merge_block` — `entities[]` is field-split (translator writes `translation_en`, llm-enrich writes `pid`), so `set_block` was silently erasing those downstream contributions on any nlp-enrich-only rerun.

### 3. The document-json bridge could silently drop the entire baseline on a `doc_id` mismatch

Found via a live e2e run (see #18 for the run link) and confirmed with the run's own intermediate JSON artifacts: `page_categories`, `content`, `source`, and `translations` all survived stages 1–3 and vanished entirely at the nlp-enrich stage.

Root cause: `atrium-translator` derives `doc_id` from the input filename (`file_path.name.split(".")[0]`), and in the e2e pipeline it's fed alto-postprocess's per-page split file (`CTX000000003-1.alto.xml`), not a whole document — so its own output declares `doc_id: "CTX000000003-1"`. `nlp-enrich`'s document-json bridge trusted that declared field to name the scratch-dir seed file, but `summarize_nt_udp.py` independently derives its own doc_id from the CoNLL-U filename (`"CTX000000003"`, correct) — a mismatch left two files in the scratch directory (the orphaned, complete baseline under the wrong name, and nlp-enrich's own fresh, baseline-less output under the right name), and the collector's `glob()` picked between them non-deterministically.

Fixed by no longer trusting the baseline's declared `doc_id` for the bridge filename at all — `nlp-enrich` now derives its own authoritative doc_id from `INPUT_TABLES_DIR` (the same source `summarize_nt_udp.py`'s `doc_name` traces back to) and uses that on both the seed and collect ends, so they always agree. Falls back to the old baseline-trusting behavior only when a single doc_id can't be determined (batch runs with multiple inputs), where there's no single correct answer anyway.

Note this doesn't fix `atrium-translator`'s `doc_id` derivation itself — that's still the known, tracked `canonical_doc_id()` gap (the four tools' four different doc_id derivations converging on one hub-provided function, not yet wired into any of them). It just means that gap can no longer silently corrupt a downstream tool's accretion.

### Net effect on the CLI-shape landscape

All five tools now converge on the same file-pair `--document-json`/`--document-json-out` shape for single-document use; directory form remains available everywhere as the legitimate batch-processing path. `canonical_doc_id()` wiring remains open and is the next real gap in this area.
