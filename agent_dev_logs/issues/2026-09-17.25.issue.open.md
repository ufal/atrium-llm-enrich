#### <img src="https://avatars.githubusercontent.com/u/65828620?u=80b39d3cb2967c52e1d4af28dcefc7a1efdfdc79&v=4" width="50">[K4TEL](https://github.com/K4TEL) opened issue at [2026-09-17 06:50](https://github.com/ufal/atrium-llm-enrich/issues/25):

### What

[`honzas83/archivatorium`](https://github.com/honzas83/archivatorium) — "a toolkit for cleaning,
formatting, and validating OCR outputs processed by LLMs", by **Jan Švec (ZČU / University of West
Bohemia, Pilsen)**. Same LINDAT/CLARIN family as us, so this can be a **cooperation** rather than a
cold third-party dependency: shared evaluation data, shared prompts, shared findings.

Four CLI commands (`ocr`, `clean`, `metadata`, `interlink`), but **only `ocr` is in scope here** —
`clean` / `metadata` / `interlink` target an Obsidian vault workflow that duplicates, in a different
shape, what `atrium-nlp-enrich` and this repo's vocabulary mapping already do. Let's not adopt those.

### Why it's worth a look for our OCR task

Verified from `archivatorium/ocr_engine.py` + `archivatorium/cli.py` @ `master`:

- **Same transport we already run.** PDF → `pdf2image` render at `--dpi` (default 300) → **Ollama**
  vision chat → Markdown. We already have `ollama_client.py`, so nothing new to stand up.
- **Four tuned prompt/sampling profiles** (`--mode standard|qwen38|glm|firered`) with per-mode system
  prompts and per-mode temperature / top-p / top-k / repeat-penalty defaults. This is the interesting
  part — it is *prompt engineering for OCR*, not just "call a VLM". Their `qwen38` system prompt
  explicitly forbids inventing Markdown heading/emphasis markers on typewritten text, marks
  unreadable spans `[unreadable]`, and pins paragraph-per-physical-line — the exact failure modes
  that make VLM transcription hard to score against our gold text.
- **Previous-page context carry-over** (`include_previous_page_context`, on for `standard`/`qwen38`,
  off for `glm`/`firered`) — worth measuring: it may help hyphenation/continuation across a page
  break, and may equally seed hallucination.
- **Remote Ollama with DigestAuth** (`--host/--user/--password`) — fits a shared GPU host.
- **Resume-by-append** on an existing per-document `.md` with page headers, plus per-page timing logs.

Default model `qwen3.5:9b`; `glm` mode needs an Ollama API server ≥ 0.9.0.

### Where it plugs in — pick the seam explicitly

Per the discipline we set in [`plans/24.plan.md`](../blob/test/agent_dev_logs/plans/24.plan.md) §B,
name the seam up front instead of conflating two comparisons:

1. **#10's render+OCR path** — archivatorium competes against **Tesseract `ces`** (landed) and
   **PERO-OCR** (next candidate) as the engine behind `pdf_to_md.py --ocr` for scanned / curve-only
   pages. ← **This issue targets (1).**
2. Hub [`atrium-project#22`](https://github.com/ufal/atrium-project/issues/22) VLM tier — its four
   modes join `plans/10.plan.md` §2c's candidate list as scored entrants. Free follow-on once (1)
   has numbers, since `bench_compare.py` scores both from the same manifest.

### What it does **not** give us

- **No geometry.** Output is page-header-delimited Markdown — no bounding boxes, no ALTO, no
  PAGE-XML. So it cannot by itself populate `atrium_document.py`'s `lines[].bbox`, and it cannot feed
  `atrium-translator`'s ALTO dual-pass reconstruction, which needs `String` coordinates. Contrast
  PERO-OCR, whose PAGE-XML maps cleanly onto ALTO/TEITOK. If we adopt it, it is a **text-plane**
  originator, and any geometry has to come from elsewhere.
- **No paradata.** No `atrium_paradata.py`-shaped run log; we'd wrap it.
- `requires-python >= 3.12` vs. our 3.11 baseline, and it pulls **`PyPDF2`** (deprecated, superseded
  by `pypdf`) plus `pdf2image` (needs system `poppler`, where we use `pypdfium2`). A wrapper at the
  `pdf_to_md.py` seam avoids importing their package into our env at all.

### Blocking gate — licence

**There is no `LICENSE` file in the repository** (checked `master` and `main`), so it is
all-rights-reserved by default. Our §2 "permissive-first" bar is not met until this is resolved.
First action is to ask the authors to add one (MIT/Apache-2.0 would match the rest of ATRIUM).
Nothing gets vendored or shipped in a Docker image before then.

### Proposed steps

- [ ] Reach out to Jan Švec — licence, current state/roadmap, and whether they want a joint
      evaluation. Offer our DU harness + archaeological gold pages; ask what they evaluate on today.
- [ ] Ask where `glm-ocr` / `firered-ocr` Ollama tags come from and what their weight licences are.
- [ ] Wrap `ocr` behind our existing seam as an opt-in backend (`pdf_to_md.py --ocr-engine

- [ ] Score all four modes with `bench_compare.py` against Tesseract `ces` on the `curves.pdf` /
      `scan.pdf` fixtures + the stratified sample, CER/WER per tier.
- [ ] Ablate `include_previous_page_context` on/off — quantify hallucination carry-over.
- [ ] Emit paradata for the wrapped runs; record model + mode + sampling params as run parameters.
- [ ] Report back to hub `atrium-project#22` with the table; decide adopt / benchmark-entrant-only /
      drop.

### Acceptance

A `bench_compare.py` report in which `archivatorium` (all four modes) and Tesseract `ces` are scored
on the same pages, plus a one-paragraph recommendation and a resolved licence answer.
