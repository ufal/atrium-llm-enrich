# [\#18 Issue](https://github.com/ufal/atrium-llm-enrich/issues/18) `open`: Build explicit `PDF`/`DOCX`-2-`JSON` converter - digital-born documents
**Labels**: `development`, `a big one`, `integration`


#### <img src="https://avatars.githubusercontent.com/u/65828620?u=80b39d3cb2967c52e1d4af28dcefc7a1efdfdc79&v=4" width="50">[K4TEL](https://github.com/K4TEL) opened issue at [2026-08-02 09:59](https://github.com/ufal/atrium-llm-enrich/issues/18):

To properly service digital-born documents and integrate them into our LLM workflows, we need to build an explicit converter for PDF and DOCX files. The converter must ingest these files, extract their textual and spatial formatting actions, and output them directly into the `atrium_document` JSON schema.

This effectively bridges the visual layout cue taxonomy developed in Issue #10 (e.g., HTML comments like `<!-- PAGE_BREAK -->`, `<!-- BBOX -->`) with the new ecosystem-wide JSON standard. 

## Context & Rationale
* The pipeline currently relies on the paradata-pair accretion model across all five stages.
* The previous DOCX/PDF to MD conversion scripts rely on Markdown with HTML comments for spatial cues. We must ensure this visual and layout data is mapped accurately into the `AtriumDocument` JSON record so it can act as the overarching schema for downstream knowledge search and retrieval.

## Tasks
- [x] Create a new entrypoint/converter script (e.g., `api_util/digital_to_json.py`) that accepts `.pdf` (digital-born) and `.docx` files.
- [x] Parse layout cues and structural borders (fonts, headers, text blocks) and map them to the corresponding fields defined in `atrium_document.schema.json`.
- [x] Ensure the script initializes a compliant `AtriumDocument` JSON object that can be safely passed to subsequent pipeline stages (like semantic enrichment or TEITOK translation).
- [x] Add unit tests utilizing both digital-born PDF and DOCX sample fixtures.

## Acceptance Criteria
- **Functionality:** The tool successfully converts a digital-born PDF and a DOCX file into a properly formatted `doc.json`.
- **Cue Preservation:** Visual layout cues (headers, page breaks, bounding boxes) are accurately parsed and populated into the correct JSON nodes.
- **Schema Validation:** The output JSON strictly passes validation against the canonical `atrium_document.schema.json`.
- **Pipeline Compatibility:** The resulting JSON can be successfully ingested by the LLM semantic enrichment module without throwing schema or structural errors.

#### GPT and Gemini reviewed the open-source landscape for the **digital-born PDF/DOCX → structured `atrium_document` JSON** requirement: 

My primary recommendation is to **avoid implementing `digital_to_json.py` as a lossy PDF/DOCX → Markdown → JSON converter.** 

Instead, we should build a **format-aware extraction layer** that parses directly into a common intermediate representation (IR), followed by a deterministic mapper into `atrium_document.schema.json`.

#### 1. Recommended Tool Stack

After evaluating options like Docling, PyMuPDF, Unstructured, pdfplumber, and MinerU, the best combination for our requirements is:

*   **Docling (Primary Foundation):** Best overall for handling both PDF and DOCX. It natively extracts hierarchy, pages, paragraphs, headings, lists, and tables into a structured representation without relying on OCR (crucial for digital-born routing).
*   **PyMuPDF (PDF Geometry Enrichment):** The strongest tool for precise extraction of PDF text blocks and bounding box (BBOX) coordinates.
*   **python-docx / docx2python (DOCX Fallback):** Only necessary if testing reveals Docling is dropping Word-specific metadata (like headers/footers or specific styles).

#### 2. Proposed Architecture

```text
                            │
             ┌──────────────┴──────────────┐
             │                             │
           .pdf                          .docx
             │                             │

             │                             │
       ┌─────┴─────┐                    Docling
       │           │                       │

             │

             │
    AtriumDocument Mapper
             │

             │
          doc.json ───► atrium-llm-enrich

```

#### 3. Key Implementation Shifts

**Replacing Legacy Layout Cues**
The old Markdown-based mechanism treated layout as inline control markers (e.g., `<!-- PAGE_BREAK -->`, `<!-- BBOX x=... -->`). Moving forward, these should be treated as **conceptual mappings**, not literal strings. A bounding box or page break should no longer be an HTML comment attached to a text fragment; they must become typed data nodes directly populated in the JSON structure.

**Digital-Born Detection Before OCR**
Routing logic should happen at the text-layer inspection stage, potentially on a **per-page basis**. If a 200-page PDF has 180 digital pages and 20 scanned pages, it should route the digital pages through Docling/PyMuPDF and only send the mixed/scanned pages to the OCR/HTR pipeline.

**Schema Validation as a Hard Gate**
The converter should never blindly write `doc.json`. Schema validation (`jsonschema.validate()`) should be built directly into the converter. If `digital_to_json.py` exits successfully, its output must be mathematically guaranteed to conform to the canonical `atrium_document` schema, protecting all downstream consumers.

#### Next Steps

Before mapping, we should review the current `atrium_document.schema.json` and the `atrium-llm-enrich` ingestion code to ensure our new BBOX, page, and style JSON nodes align perfectly with the existing contract (or determine if a schema extension is required).
