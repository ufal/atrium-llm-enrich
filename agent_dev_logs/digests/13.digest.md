## 2. The contract, as it now stands

Unchanged from the settled design, restated for reference. Three planes, one job each:

- **Reading — annotated Markdown** (`# doc` + `## Page N` + `<!-- cues -->`): the LLM diet, **derived & disposable**.
- **Layout — TEITOK.XML**: the **spatial source of truth**.
- **Search — the JSON `AtriumDocument` record**: the **canonical semantic record**, built by **accretion** (motyc's redirect, 2026-07-24), not by an aggregator service.

```
doc.json ──► [pc] ──► [alto] ──► [translate] ──► [nlp] ──► [llm] ──► doc.json
        page_categories  pages/lines/content  translations   entities   enrichment
```

**Six rules**: ① optional baseline in / record out · ② **own block only** · ③ no baseline → own part only · ④ per-block stamp (`program`/`run_id`/`paradata_ref`) · ⑤ licences accrete most-restrictive · ⑥ unknown/newer blocks preserved, newer major refused.

Ownership is declared in three module-level maps in `atrium_document.py`: `BLOCK_OWNERS` (7 blocks), `BLOCK_FIELD_OWNERS` (field splits inside `pages`/`lines`/`entities`), `BLOCK_KEY_FIELDS` (natural keys for merging).

## 4. Per-repo summary

### 4.1 `atrium-project` — the hub 🟡

**Role.** Owns `docs/templates/shared/atrium_document.py` (589 lines), `atrium_document.schema.json` (292 lines, draft 2020-12), `docs/document_schema.md`, and `fixtures/atrium_document.example.json`. Enforces byte-parity through `para-drift.reusable.yml`.

**What is right.** The fixture **validates cleanly** against the schema (0 errors, checked with `jsonschema` 4.26). The prose in `document_schema.md` states the six rules precisely. The version guard, the `migrate_document()` branch point, and `merge_document_records()` (newest-wins per block) are all in place before they are needed — the same discipline `atrium_paradata.py` set.

**What is wrong.**

- **The template does not enforce its own rule 2.** `_assert_owner()` (line 299) checks only `BLOCK_OWNERS`. A block that *also* appears in `BLOCK_FIELD_OWNERS` — `pages`, `lines`, `entities` — is field-split by design, yet its nominal owner may still call `set_block()` on it and wipe every co-contributor's fields. Reproduced against the canonical template:

  ```
  after translator:      [{page:1, line:14, char_span:[21,37], surface:'kostel', translation_en:'church'}]
  after nlp set_block(): [{page:1, line:14, char_span:None,    surface:'kostel'}]        ← translation_en gone
  ```

  This is not a hypothetical: nlp-enrich (§4.5) and alto's API (§4.2) both do exactly this. The template is the right place to close it.

- **`BLOCK_FIELD_OWNERS` and the schema disagree.** The table grants nlp-enrich `lemma`, `upos`, `feats` on `lines[]`; the schema's `lines[]` properties list none of them. `additionalProperties: true` means it validates anyway — so validation will never surface the divergence.

- **The docstring teaches the private accessor.** The worked example at line 139 reads `run_id=logger._run_id`. Every downstream repo copied it.

- **`ParadataLogger` has no public `run_id`.** Only `get_license_block()` was added. The 2026-07-26 recommendation to "replace `_logger._run_id` with `_logger.run_id`" is therefore **not actionable as written** — the property must be added to `atrium_paradata.py` first. One repo has already written `logger.run_id` on the assumption it exists (§4.2).

- **The e2e smoke ignores the document plane entirely.** `e2e-pipeline-smoke.yml` chains all five tools over a shared fixture across 556 lines and contains **zero** occurrences of the string `document`. The one workflow positioned to catch every finding in this digest does not look.

### 4.2 `atrium-alto-postprocess` — CLI correct, API not 🟡

**Role.** Owns `pages[]` (quality score/band, `needs_ocr`, `ocr`, `canvas`), `lines[]` (`categ`, `quality_score`, `lang`, `text`), and `content`. Enablement is config-driven via `[DOCUMENT].JSON_DIR` / `DOCUMENT_JSON_DIR`, which switches every stage on at once — the cleanest enablement model of the five.

**What is right.** All seven live stage scripts (`page_split`, `aggregate_STAT`, `classify_TEXT`, the four `extract_*`) route through `document_hook.write_document_block()`, which uses `DocumentRecord` properly and calls `merge_blocks` for `pages`/`lines`. `_lines_records_from_df()` is a model projection: key fields plus owned fields only, omitting absent values rather than writing placeholders. The `PROGRAM_NAME = "alto-postprocess"` normalisation (so stage-level paradata names like `langID-classify` don't leak into block provenance) is done and documented. It is also the only repo to have wired `set_source()`.

**What is wrong.**

- **The API surface breaks the contract the CLI honours.** `service/text_api.py:220` passes `set_blocks={"pages": …, "lines": …}` where every CLI stage passes `merge_blocks=`. Reproduced: `set_block("pages", …)` after page-classification has run leaves `[{page:'1', quality_score:0.98, quality_band:'Clear'}]` — `category` and `category_confidence` are gone. Same for nlp's `teitok_surface`.

- **Two dead functions encode a superseded design.** `write_document_record()` (lines 43-121) and `update_document_record()` (124-197) bypass `DocumentRecord` entirely, hand-roll dict manipulation, and write `assembled.source_run_ids` and `assembled.mode: "view"` — keys from the **rejected aggregator draft**, not the shipped `assembled.blocks{}`. They also assign `provenance.license_detail` directly, bypassing the most-restrictive union of rule 5, and set `doc["lines"] = lines_data` wholesale. Only `write_document_record` is referenced, and only from `tests/test_document_hook.py`.

- **`write_document_record()` would raise if it were ever called.** Line 60 reads `logger.run_id`; `ParadataLogger` exposes only `_run_id`. The three tests pass a `MagicMock`, which answers any attribute — so the test suite certifies code that cannot run.

- **Inconsistent within one file.** `paradata_ref_for()` (line 220) uses `logger._run_id`; `write_document_record()` uses `logger.run_id`.

- **Stale docstring, still.** The module header's "Ownership note" (line 17) says `PROGRAM = "alto-postprocess"`; the constant is `PROGRAM_NAME` (line 40). Flagged on 2026-07-26, unfixed.

### 4.3 `atrium-page-classification` — the reference implementation 🟢

**Role.** Owns `page_categories` (whole block) and `pages[].category` / `pages[].category_confidence` (field-level).

**What is right — and worth copying.** `atrium_document_adapter.py` is the only integration that gets the whole contract right at once:

- It uses `merge_block("pages", …, own_fields=["category", "category_confidence"])` — never `set_block` on a field-split block.
- It uses the **public** `get_license_block()`.
- It **splits the two CLI shapes into two functions** rather than overloading one pair of kwargs: `write_document_record()` for file-pair semantics, `write_document_records_dir()` for directory semantics. Every other repo picks one shape and cannot do the other.
- It handles **chunked self-runs**: when a document's pages straddle two chunks of the same run, the baseline is re-read from the *output* dir so a later chunk cannot clobber an earlier one. No other repo considers this.
- It **writes atomically** (`tmp` + `replace`), with the reasoning recorded in a comment: a crash mid-write would leave a corrupt record for the next tool to trip over in `load_document()`. The shared `finalize()` writes in place, so no other repo has this protection.

**What is wrong.** Minor. `_run_id_and_ref()` (line 65) reaches for the private `_run_id` while line 113 uses the public licence accessor — half-migrated. And `page_categories` duplicates `pages[].category`: both are written from the same `CLASS-1` column in the same loop, so they cannot disagree today, but nothing prevents a future writer from updating one and not the other.

### 4.4 `atrium-translator` — schema contradiction and dead code 🔴

**Role.** Owns `translations` and `entities[].translation_en`.

**What is right.** Full CLI (`--document-json` / `--document-json-out`) and API (`document_json` multipart part, multipart/mixed response) support. `add_derived_from("translated_xml", …)` is correct. `tests/test_atrium_document.py` passes locally (4/4).

**What is wrong.**

- **`translations` is written in a shape the schema does not describe.** `utils.py:159` and `:496` both do:

  ```python
  doc.set_block("translations", {tgt_lang: "\n\n".join(translated_texts).strip()})
  ```

  The schema and the hub fixture both define `translations` as `{source_lang, target_lang, backend}` — language-pair *metadata*. The implementation instead inlines **the entire translated corpus text** under a language key. `additionalProperties: true` lets it validate, so nothing catches it. It also contradicts the reference discipline: the translated text already persists as `derived_from.translated_xml`, and the record is not meant to carry megabytes of body text. Two writers, one for the ALTO path and one for the metadata path, would also overwrite each other; a second target language wipes the first.

- **The entity-translation pass is dead code in the canonical pipeline.** The declared order is `pc→alto→translate→nlp→llm`. `entities[]` is produced by **nlp-enrich**, which runs *after* the translator. So `existing_entities = doc._data.get("entities")` is always empty at translate time and the whole block (utils.py:161-175, 498-512) never executes. If the order were reversed to make it fire, nlp's `set_block("entities", …)` would then destroy the result (§4.5). Either way the field never survives — consistent with the hub fixture, whose `entities[0]` carries no `translation_en`.

- **Private access to `DocumentRecord` internals.** `doc._data.get("entities")` — the template offers no public per-block reader, only `to_dict()`. This is an API gap as much as a violation.

- **Dynamic field name outruns the ownership table.** `own_fields=[f"translation_{tgt_lang}"]` produces `translation_de`, `translation_fr`, … for any non-English target. `BLOCK_FIELD_OWNERS["entities"]["translator"]` lists only `translation_en`, and so does the schema. `merge_block` will happily write it (the caller-supplied `own_fields` overrides the table), so a non-EN run silently populates a field no consumer knows about.

- **The licence guard is inverted.** `main.py:299`: `if hasattr(_logger, "_license_block"): doc.add_license_detail(_logger.get_license_block())` — it *guards on the private name* and *calls the public one*. When `_license_block` is eventually removed from `atrium_paradata.py`, licence accretion stops silently. The comment above it still reads "Known wart: retrieve the license detail using the private logger call", which is no longer what the code does.

- `paradata_ref` is still built from `_logger._run_id` (main.py:245).

### 4.5 `atrium-nlp-enrich` — the chain breaks here 🔴

**Role.** Owns `entities[]`, `lines[]` morphology fields, `pages[].teitok_surface`, and `derived_from.teitok`.

**What is wrong.** This is the most serious set of findings in the audit, and none of it is visible to the existing test.

- **The record is written to the wrong place.** `run_document_hook()` declares an `out_json: str` parameter (line 16) and **never references it again** — grep for `out_json` in `api_util/document_hook.py` returns exactly one hit, the signature. The body opens `DocumentRecord.open(doc_id, "nlp-enrich", baseline=…, run_id=…, paradata_ref=…)` with **no `out_dir`** and never calls `finalize(out_json)`, so the context manager's `__exit__` falls through to the default `out_dir="."` and writes `<doc_id>.document.json` into the **process working directory**. The caller (`summarize_nt_udp.py:536-537`) computed `out_json = baseline_json` for in-place accretion; that path is simply never used. Net effect: nlp-enrich's `entities` never reach the shared directory, and llm-enrich reads a baseline with no entities in it. The chain is broken at stage 4 of 5.

- **`set_block("entities", …)` destroys co-owned fields.** Line 100. `entities[]` is field-split three ways (nlp-enrich / translator / llm-enrich). Reproduced above in §4.1.

- **`char_span` is always `None`, and it is a merge key.** Line 78 hardcodes `"char_span": None` with the comment "Derived later if needed by LLM". But `BLOCK_KEY_FIELDS["entities"] = ["page", "line", "char_span"]`, so with `char_span` constant the natural key collapses to `(page, line)`. Reproduced with the canonical template — three distinct entities on line 14 of page 1:

  ```
  3 entities on one line, char_span=None -> merged rows: 1
  [{'page': '1', 'line': 14, 'char_span': None, 'surface': 'C'}]
  ```

  Two of three entities silently vanish the moment any downstream tool calls `merge_block("entities", …)`. On a real archaeological page, multiple named entities per line is the normal case, not the exception.

- **It writes a field it does not own.** Line 80 emits `"pid": {wikidata, geonames, aat, amcr}` (all null). `pid` belongs to llm-enrich per `BLOCK_FIELD_OWNERS`. Because it comes via `set_block`, `_assert_owner` never checks it.

- **The `include_lines` flag is inert.** Lines 109-113: it logs a warning about duplicate-row risk, then `pass`. `api_4_stats.sh:48` passes `$INCLUDE_LINES` through to a switch that does nothing. Honest as a placeholder, but it means `lines[].lemma/upos/feats` — granted by the ownership table — are never written by anyone.

- **The test cannot catch any of this.** `tests/test_document_hook.py:10` patches `api_util.document_hook.DocumentRecord` with a `MagicMock`. It asserts the hook was *called*, never what it produced or where. 3/3 pass.

### 4.6 `atrium-llm-enrich` — complete, with residue 🟡

**Role.** Owns `enrichment` and `regenerable.markdown`; issue #13 lives here.

**What is right.** The scope gap reported on 2026-07-26 is **closed**. All four execution surfaces now participate:

| Surface                                | Enable                                  | Call site                  |
|----------------------------------------|-----------------------------------------|----------------------------|
| `llm_run.py` (local vLLM/transformers) | `DOCUMENT_JSON_DIR` in `llm_config.txt` | `:500`                     |

## 5. The JSON-to-MD converter for llm-enrich — recommendation: **build it** (`api_util/json_to_md.py`)

`api_util/` already holds the whole Markdown front-end: `pdf_to_md.py`, `docx_to_md.py` (originals → MD), `xml_to_md.py` (TEITOK/ALTO → MD), `doc_to_visual_md.py` (dispatcher), and `layout_md.py` (the 15-cue `CUE_SCHEMA` + 8 inline GFM forms, single source of truth). There is no path from the JSON plane back to the reading plane. Five reasons it should exist:

**① It closes the `regenerable` loop, which is currently open.** Today llm-enrich writes `regenerable.markdown = {from: <TEITOK path>, converter: "doc_to_visual_md", detail: "full"}`. That recipe points at a *persistent step output the record merely references* — a catalogue consumer holding only the JSON cannot execute it. With `json_to_md`, the recipe becomes `{from: "<doc_id>.document.json", converter: "json_to_md@1.0", detail: "full"}` and the record becomes **self-regenerating**. That is the difference between a FAIR record and a record with a dangling pointer.

**② The work is a projection, not a renderer.** `xml_to_md.rows_to_layout_markdown(rows, pages, title)` already consumes exactly `{page_num, line_num, text, bbox}` rows plus a `{page: {width, height, figures}}` map. The record's `lines[]` carries `page`/`line`/`text`/`bbox`, and `pages[]` carries `canvas{width,height,unit}`. The converter is ~60 lines of key renaming plus a call into the existing renderer — no new cue vocabulary, no new rendering code, no drift risk against `layout_md`.

**③ The JSON path can emit cues no other converter can.** `NEEDS_OCR` and `OCR: engine=…, lang=…` are defined in `CUE_SCHEMA` but unfillable from XML — they live in `pages[].needs_ocr` and `pages[].ocr`, which only the record carries. And because `lines[].categ` and `lines[].quality_score` are present, `json_to_md` can **drop** `Garbage`/`Inverted` lines and offer `--min-quality`, so the JSON path produces a *better* LLM diet than the XML path rather than an equivalent one.

**④ It is the natural home for the `--detail` knob.** `full` / `standard` / `minimal` are already an enum in the schema's `regenerable.detail` and still unimplemented (deferred item §E). Implementing three profiles once in a new converter is far cheaper than retrofitting three existing ones.

**⑤ It gives nlp-enrich MD input without duplicating a converter.** Digest §D.1's oldest open item is that nlp-enrich still feeds its LLM plain CSV lines. If MD regenerates from the *shared* document JSON, both LLM-bearing tools read one artifact through one converter.

**Two constraints to build in.**

- **No self-feeding.** llm-enrich both writes `enrichment` and would read the record. `json_to_md` must read only `pages`, `lines`, `content` and **never** `enrichment` — otherwise a second run feeds the model its own prior output.
- **A documented fallback ladder.** Page-sectioned MD needs `lines[]`, which only exists if alto's `classify_TEXT` stage ran. Fall back `lines[]` → `content.text` (unsectioned) → explicit error. Silently emitting a structureless dump would be worse than failing.

Register it in `doc_to_visual_md.py`'s dispatcher for `*.document.json` so there stays exactly one entry point.

## 6. Adaptation capacity of the `atrium_document` template for other JSON schema designs

**Question asked:** how much of `atrium_document.py` is reusable machinery, and how much is ATRIUM-specific? **Answer: the mechanism is fully schema-agnostic; the binding to *this* schema is ~50 lines of module-level constants — but there is no injection point, so adaptation means forking the file, and two schemas cannot coexist in one process.**

**Generic, reuse-as-is (≈480 of 589 lines).** None of this knows what an ATRIUM document is:

| Mechanism                                                    | Why it generalises                                                                       |
|--------------------------------------------------------------|------------------------------------------------------------------------------------------|
| Baseline deep-copy + own-block write                         | Pure structural accretion                                                                |
| `merge_block()` field-level merge                            | `key_fields` and `own_fields` are **parameters**; only the *defaults* come from the maps |
| `_stamp()` → `assembled.blocks{}`                            | Provenance keyed by arbitrary block name                                                 |
| `to_dict()` rule-6 pass-through                              | Any unrecognised key is preserved verbatim                                               |
| `load_document()` major-version guard + `migrate_document()` | Version policy, not content policy                                                       |
| `merge_document_records()`                                   | Newest-`updated_at`-wins fold, block-agnostic                                            |
| `_sanitise()`, context manager, `finalize()`, the CLI shim   | Infrastructure                                                                           |

Critically, **the module never validates against `atrium_document.schema.json`**. The schema is documentation and a CI fixture, not a runtime dependency. So a different JSON design inherits the entire mechanism for free.

**ATRIUM-specific, must be edited to retarget (≈50 lines, all in one screen at the top of the file):**

1. `BLOCK_OWNERS` — 7 ATRIUM block names → 5 ATRIUM tool names (lines 61-69)
2. `BLOCK_FIELD_OWNERS` — the `pages`/`lines`/`entities` field splits (73-97)
3. `BLOCK_KEY_FIELDS` — natural keys per list block (100-104)
4. `to_dict()`'s `order` list — 15 hardcoded ATRIUM block names (366-382)
5. `RESERVED_KEYS`, `RECORD_TYPE`, `FILE_SUFFIX`, `LICENSE_NAME`/`LICENSE_URL` (46-57)
6. `doc_id` as the mandatory primary-key *name* (158, 171)
7. `set_source()`'s first-writer-wins "original input" semantics (207-220)
8. `from para_licenses import merge_effective_licenses` in `_provenance()` — a Creative-Commons-shaped concept wired into the core (328-338)

**Three real limits, in order of consequence.**

- **No injection point.** `_assert_owner()` and `merge_block()` read the module globals directly. You cannot pass a different ownership map at construction time. Adaptation is therefore *fork the file and edit the constants* — cheap and honest for a second, unrelated schema; unworkable if one process must handle two schemas (e.g. a per-document record and a per-collection record in the same service), because the maps are global state.

- **It does not enforce the schema it describes.** `_assert_owner` only *warns* unless `strict=True`, and — the hole that produced §4.1, §4.2 and §4.5 — `set_block()` is permitted on blocks that `BLOCK_FIELD_OWNERS` declares field-split. Any reuse inherits that permissiveness. A retargeted copy should fix it at the same time.

- **Licences are hardwired into provenance.** `_provenance()` calls `merge_effective_licenses` unconditionally when blocks are present, and falls back to a CC BY-NC 4.0 default with a hardcoded note. A non-ATRIUM design that has no licence dimension carries a spurious licence block.

**Recommended shape if reuse is actually wanted** — a `BlockPolicy` dataclass carrying `{owners, field_owners, key_fields, reserved, order, record_type, file_suffix, id_field, license_merger}`, defaulted to `ATRIUM_POLICY` and accepted as `DocumentRecord(..., policy=…)`. Roughly 40 lines, fully backward-compatible (every existing call site keeps working untouched), and it converts all three limits at once: multi-schema processes become possible, `strict` block-shape enforcement becomes a policy field, and the licence merger becomes optional.

**Bottom line.** As a *pattern*, `atrium_document.py` transfers to any accretion-shaped JSON design essentially unchanged — the paradata-pair mechanism is the reusable asset. As *code*, it transfers by forking: budget one file, ~50 lines, half a day, and accept one schema per process. The `BlockPolicy` refactor is what would turn it from a template into a library, and it is small enough to be worth doing before a second schema exists rather than after.

## 8. Cross-cutting findings (no single repo owns these)

- **`doc_id` — the record's primary key — is derived four different ways.** `translator`: `name.split(".")[0]` · `llm-enrich` ollama/openrouter: `Path.stem` · `llm-enrich` `llm_run`: `teitok_read.doc_id_from_path()` · `nlp-enrich`: `Path.stem` · `page-classification`: the `FILE` column. Demonstrated divergence:

  | filename                     | `Path.stem`           | `split(".")[0]` |
  |------------------------------|-----------------------|-----------------|
  | `CTX000000001.alto.xml`      | `CTX000000001.alto`   | `CTX000000001`  |
  | `CTX000000001.udpipe.conllu` | `CTX000000001.udpipe` | `CTX000000001`  |
  | `CTX0001.teitok.xml`         | `CTX0001.teitok`      | `CTX0001`       |

  On any multi-dot filename two tools produce different keys and the chain silently forks into two records. Nothing detects it.

- **Two incompatible I/O conventions.** File-pair `--document-json` / `--document-json-out` (translator, page-classification single-doc) versus in-place directory `--document-json-dir` (alto, llm-enrich, nlp-enrich). Rule 1 in `document_schema.md` names only the file-pair form. Only page-classification implements both. A pipeline driver must special-case each tool.

- **Non-atomic writes everywhere but one.** The shared `finalize()` writes in place; only page-classification does `tmp` + `replace`. A crash mid-write leaves a corrupt record that fails the next tool's `load_document()`.

- **Zero cross-repo coverage.** No repo runs pytest in CI, and the hub's five-stage `e2e-pipeline-smoke.yml` never mentions the document JSON. Every 🔴 finding above requires exactly one thing to catch it: a test that runs two tools in sequence and inspects the record. That test does not exist in any form.
