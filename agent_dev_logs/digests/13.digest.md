## 2. A live incident, resolved during the push itself

While verifying the push, `atrium-translator` briefly landed a commit (`b95c6f2`) whose `atrium_paradata.py` was **missing** the `run_id` public property the hub template (and `translator/main.py`'s own already-updated code) depends on. Confirmed by hand:

```
>>> ParadataLogger(program="translator", config={}, paradata_dir=d).run_id
AttributeError: 'ParadataLogger' object has no attribute 'run_id'
```

**GitHub Actions' `Paradata Canonical Drift` check caught it within the same CI run** — `completed / failure` at `b95c6f2` — and a follow-up commit (`ac704ad`, four minutes later) restored byte-parity. All seven checks (`Paradata Canonical Drift`, `pre-commit`, `Workflow Policy Lint`, `Security Scans`, `API Meta-Contract`, `Docker Build & Push`, `CodeQL`) are green at the current HEAD, and the manual repro above now returns a real run_id.

**Why this matters for the digest, not just as trivia:** the local test suite at the *broken* commit reported **357 passed, 0 failed** — a false green. Every test that touches `ParadataLogger.run_id` either calls the private `_run_id` directly or goes through a hand-written `FakeParadataLogger` test double that defines its own `run_id` regardless of what the real class exposes. No test in the repo instantiates the real `ParadataLogger` and reads the real public `.run_id` the way `main.py` actually does. `para-drift` — a byte-diff against the hub, not a unit test — was the only thing in the whole CI matrix positioned to catch this, and it did. This is direct, live evidence for the plan's P1.5 recommendation (put these mocked-boundary tests under real exercise) rather than a hypothetical risk.

## 3. What changed, per repo (landed and CI-green at the HEADs above)

### `atrium-project` (hub)
- `atrium_document.py`: `set_block()` now warns when called on a field-split block (`pages`/`lines`/`entities`) instead of silently permitting the exact mistake that broke nlp-enrich and alto's API path. Added `get_block()` (read-only, deep-copied), `canonical_doc_id()` (one doc_id derivation to converge the five tools' four different ones onto), and atomic `finalize()` writes (`.tmp` + rename).
- `atrium_paradata.py`: added the public `ParadataLogger.run_id` property alongside the existing `get_license_block()`.
- `atrium_document.schema.json`: `lines[]` now documents `lemma`/`upos`/`feats` (already granted to nlp-enrich in the ownership table, previously undocumented in the schema).
- `docs/document_schema.md`: changelog section recording all of the above.

### `atrium-alto-postprocess`
- `service/text_api.py`'s document-JSON API path used `set_blocks` on `pages`/`lines` — both field-split blocks shared with page-classification/nlp-enrich — which silently erased their contributions on every API call. Now uses `merge_blocks`, matching what every CLI stage in this same repo already did correctly.
- Deleted `write_document_record()`/`update_document_record()` (~150 lines): two functions that bypassed `DocumentRecord` entirely, wrote keys from the rejected aggregator draft (`assembled.source_run_ids`, `assembled.mode`), and were called from nowhere except their own now-deleted tests — one of which was silently broken (assigning to a since-read-only property) and never noticed because it only ran against a `MagicMock`.
- All `logger._run_id` reads (7 call sites across 6 files) migrated to the public `logger.run_id`; the module docstring's stale `PROGRAM` → `PROGRAM_NAME` typo fixed.

### `atrium-nlp-enrich` — most substantial fix of the six
`run_document_hook()` could not have produced a single entity in production before this fix: `parse_and_align_conllu()`'s return shape (`{"sentences": [...]}`) was passed straight into code expecting a flat token list (`KeyError` on the first non-entity token via a nonexistent `span["type"]` key), `alto_path` was never threaded through (so bboxes/pages were always empty even if the above were fixed), and `char_span` was hardcoded `None` — collapsing any two entities sharing a line into one row under the merge key. All fixed: correct flattening, a new `_augment_tokens_with_position()` deriving stable per-page line numbers and real character offsets, tagset detection via membership in the module's own `CNEC_TO_CONLL` dict (precise, not a heuristic), and `set_block` → `merge_block` for the field-split `entities` block. The existing test suite had mocked both `parse_and_align_conllu` and `group_ner_spans` with a shape neither function actually returns — replaced with real integration tests against actual ALTO+CoNLL-U content.

### `atrium-translator`
- `translations` was written as `{tgt_lang: "<entire translated corpus text>"}`, contradicting the schema's `{source_lang, target_lang, backend}` and duplicating text already persisted via `derived_from.translated_xml`. Fixed in both `process_metadata_xml`/`process_alto_xml`.
- The per-entity translation pass was dead code: in the declared pipeline order (`pc→alto→translate→nlp→llm`), `entities[]` doesn't exist yet when the translator runs, so `existing_entities` was always empty. Removed rather than reordering the pipeline or inventing a second translator stage — both are product decisions, not implementation fixes.
- The license-accretion guard tested for the *private* `_license_block` attribute while calling the *public* `get_license_block()` method — inverted, and would have broken silently the day the private name was ever removed. Now calls the public method unconditionally. (The `run_id` regression described in §2 belongs to this repo's push history and is now resolved.)

### `atrium-page-classification`
Smallest change: `atrium_document_adapter.py`'s one remaining private accessor (`_run_id`) migrated to public `run_id`. This repo's adapter was already the reference implementation in the prior audit (correct `merge_block` usage, atomic writes, chunk-straddling handling) — nothing else needed touching.

### `atrium-llm-enrich`
- Fixed the last two private `logger._license_block()` calls (in `ollama_client.py`/`openrouter_client.py`) and all four `_run_id` reads; all four `write_document_record()` call sites now compute and pass `paradata_ref` (previously always empty).
- **New**: `api_util/json_to_md.py` — converts an `AtriumDocument` JSON record directly to the same annotated-Markdown vocabulary the TEITOK/PDF/DOCX converters already produce, reusing `xml_to_md.rows_to_layout_markdown()` rather than re-implementing rendering. Reads only `pages`/`lines`/`content` — verified by test that it never reads back its own `enrichment` block (which would feed the model its own prior output on a second run). `write_document_record()`'s `regenerable.markdown` recipe now points at the document's own JSON via `json_to_md@1.0` for document-level runs, making the record self-regenerating instead of referencing a TEITOK/PDF/DOCX file a JSON-only consumer might not hold.

## 6. Third pass (2026-08-01) — P1.2 done from a stale base; a branch-divergence finding

> _Separate agent session, working branch `claude/gha-workflows-review-strategy-y8euz2`, created from each repo's **default HEAD branch** (`master`/`main`/`vit` depending on repo) at the commit noted per-repo below — **not** from `test`. This was discovered partway through, not planned; see the caveat at the end of this section before trusting anything here as already covering `test`._

**What landed, against the default-branch base:**

- **`atrium-nlp-enrich`** (`master` @ `9d9ce5e`): `run_pipeline.py` gained `--document-json`/`--document-json-out` file-pair flags (P2.2 — the directory-only tools converging on page-classification/translator's shape), wired through a scratch-dir wrapper around the existing `--document-json-dir` mechanism. Separately, `api_util/document_hook.py`'s entity extraction was found completely non-functional against real data — `parse_and_align_conllu()` returns `{"sentences": [...]}`, but the function had been consuming it as a flat token list (`KeyError: 0` inside `group_ner_spans` on any non-empty CoNLL-U), `alto_path` was never threaded through so bboxes/pages always fell back to `"1"`/defaults even when the crash was worked around, `group_ner_spans` groups *every* token (not just entities) and tags spans `kind`/`code`, not `type` (a second, independent `KeyError`), and `char_span` was hardcoded `None`. All fixed — flatten `sentences`, thread `alto_path` from `summarize_nt_udp.py`'s existing `alto_dir`, filter to `kind == "name"` spans, derive `is_cnec` from span codes against `CNEC_TO_CONLL`, and compute a real `char_span` by finding the entity surface's offset within its own reconstructed ALTO line text.
- **`atrium-alto-postprocess`** (`master` @ `9804c58`): same class of bug as nlp-enrich's *original* one — `--document-json`/`--document-json-out` were declared in argparse but never read anywhere; every stage script (`page_split.py`, `extract_*.py`, `classify_TEXT.py`, `aggregate_STAT.py`) only honors the working `--document-json-dir`/`DOCUMENT_JSON_DIR` mechanism. Fixed with the same scratch-dir wrapper pattern. Verified live against a real fixture through split→stats→extract.
- **`atrium-llm-enrich`** (`main`/`test`, same commit `2057623` — no divergence here): `openrouter_client.py` gained `--document-json`/`--document-json-out` (P2.2), single-file-only, wrapping the existing `--document-json-dir` path the same way.
- **`atrium-project`**: `e2e-pipeline-smoke.yml` (P1.2) rewritten to actually thread a document JSON through all five stages as published Docker images, restoring the real file inputs (rendered page image, alto's `--config`, translator's real per-page ALTO input, nlp's `--config` + `DOC_LINE_CATEG` bridge, llm's `-remote` image + explicit `openrouter_client.py` entrypoint arg + `OPENROUTER_KEY` gating) that a document-json baseline alone cannot substitute for. `tools/e2e/e2e_assert.py`'s entity check was also fixed — it looked for entities nested under `lines[].entities`, but the schema defines `entities` as its own top-level block; the assert script's assumption was wrong, not `document_hook.py`'s `set_block("entities", ...)` placement.

**The divergence finding, found while writing this section:** `atrium-nlp-enrich`'s `origin/test` (`6ec1b34`, already described in §3 above as "landed, pushed, CI-verified" on 2026-07-31) **already contains an independent fix for the exact same `document_hook.py` bugs** — same root causes (flatten `sentences`, thread `alto_path`, filter `kind == "name"`), but a more robust `char_span`: a running character cursor (`_augment_tokens_with_position`) walking tokens in document order, rather than this pass's substring-search (`line_text.find(surface)`), which can misplace a repeated surface string within its line. `atrium-alto-postprocess`'s `test` branch, by contrast, does **not** have the `--document-json`/`-out` wiring fix — that one really is net-new. `atrium-llm-enrich` has no divergence at all (`main` == `test`).

This session's branch was created from each repo's plain default HEAD branch without checking whether `test` — which the pre-rewrite `e2e-pipeline-smoke.yml` and this very plan (§P0, "promoting `test` to `main`") both already treat as **the ecosystem's authoritative integration branch** — was further ahead. It was, for at least one of the five repos touched here.

**Reconciled (same day, hand-merge not a git rebase):** `atrium-nlp-enrich`'s `document_hook.py` now matches `test`'s approach — `merge_block("entities", ...)` instead of `set_block`, and the cursor-based `char_span`/page/line via `_augment_tokens_with_position`. In reconciling, found that this session's fix had also added a `"type"` field to each entity record to satisfy `e2e_assert.py` — but `atrium_document.py`'s `BLOCK_FIELD_OWNERS["entities"]["nlp-enrich"]` doesn't list `"type"` as a field nlp-enrich may write, so `merge_block` would have silently dropped it, and the schema never defined such a field in the first place (only `type_onto`/`type_cnec`/`type_teitok`). Fixed the actual root cause instead: `e2e_assert.py` now checks `type_onto`/`type_cnec` presence, matching what the schema and `merge_block`'s field ownership actually carry. `run_pipeline.py`'s file-pair flag wiring (not duplicated on `test`) is unaffected and kept as a normal forward commit on top.

A **content-level reconciliation**, not a `git rebase onto origin/test` — this session's branch keeps its own commit history and default-branch base; only `document_hook.py`'s and `test_document_hook.py`'s content were brought in line with `test`'s already-reviewed approach. `atrium-alto-postprocess`'s and `atrium-llm-enrich`'s changes needed no reconciliation (confirmed not duplicated on their `test`/`main`). See `13.plan.md` §P4 for the residual branch-strategy question this doesn't resolve (which branch a PR should actually target).
