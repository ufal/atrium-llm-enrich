## 🎯 Goal
* Build an explicit converter (`api_util/digital_to_json.py`) that ingests digital-born `.pdf` and `.docx` files, extracts their structural and spatial layout formatting, and outputs them directly into the strict `atrium_document.schema.json` format for seamless LLM workflow integration.

## 🧭 The answer in one picture
* **Separate extraction, unified serialization.** A `PDF Adapter` (Docling + geometry) and a `DOCX Adapter` (Docling + OOXML fallback) → `Normalized DigitalDocument` → `AtriumDocument Serializer` → `Schema Validation` → `LLM Enrichment`.
* **One originator role per block, chosen per document.** `pages`/`content`/`lines`/`tables` describe a document's *positional plane*, and there are two ways to acquire one — OCR/ALTO or direct digital extraction. They are mutually exclusive per document, so `BLOCK_OWNERS` lists both candidates and `source.origin` decides.
* **Validation is a gatekeeper, but not a sufficient one.** No `doc.json` is emitted if `jsonschema.validate()` fails — *and* a round-trip assertion runs first, because the schema requires only `page`+`line` on a `lines[]` row and therefore cannot catch a field-ownership drop.
* **Semantic vocabulary over raw HTML comments.** Legacy Issue #10 cues map to JSON nodes rather than being copied over. Coming back the other way, a `group_id` boundary renders as a **blank line** — Markdown's native paragraph primitive — so no new cue was needed at all.

## ✅ §1a resolved — how, and why not the two obvious ways

`BLOCK_OWNERS` was conflating *who is authoritative for a block's semantics* with *who happens to originate it first*. For the positional plane those differ, and the second question already had an answer in the record: **`source.origin`**, already first-writer-wins in `set_source()`, already carrying `digital-born-pdf` / `docx` / `ocr:…` / `ABBYY-ALTO` as examples.

So `BLOCK_OWNERS` values may now be a tuple, `ORIGIN_ORIGINATORS` maps an origin prefix to its authorized originator, and `_assert_origin_consistent()` enforces it on **both** `set_block()` and `merge_block()` — the latter mattering because `merge_block()` never called `_assert_owner()`, so `pages` and `lines` were never ownership-checked at all. The check is self-guarding, so it is a no-op for every pre-#18 caller.

* ❌ **No-op alto passthrough** — would stamp `assembled.blocks[…].program = "alto-postprocess"` and add a `provenance.contributors[]` entry for a run that did nothing, in a record built for FAIR catalogue export. Rule 4 exists for attribution granularity; this falsifies it. It also puts the alto container back on the digital-born critical path.
* ❌ **A second name with no further guard** — `content` and `tables` aren't field-split, so either originator could `set_block()` over the other's. Mutual exclusivity would stay an unwritten assumption.
* ✅ **Originator role + `source.origin`** — and *not* the `assembled.blocks` stamp, because rule 4 makes that stamp name the **most recent** writer, so nlp-enrich merging into `lines[]` erases the originator signal.

**No `SCHEMA_VERSION` bump.** Versioning rule 2 ("changing block ownership" → major) is amended to say why: **widening write authorisation is additive; re-attributing an already-written block would not be.** No field renamed or removed, every record still valid, every tool keeps every capability.

**`llm-enrich-digital` → `digital-convert`.** These identities are roles, not repos, and they land permanently in `provenance.contributors[].program` on export.

## 🚨 Three defects found while implementing the decision

### §0b — ✅ CLOSED: the `group_id` change had landed in the hub copy only
`para-drift.reusable.yml` `diff -u`s `atrium_document.py` **and** `atrium_document.schema.json` against every tool repo. Both pairs currently differ: `group_id`, `tables`, `forms` and the digital field grant are in `docs/templates/shared/` and absent from the llm-enrich root copies. Either red now or red the instant `v1` moves — and per #13's TODO list **no repo runs pytest in CI**, so para-drift is the only gate that would catch it. Separately, `tables` and `forms` were added to the hub schema and module with no entry in the plan, this digest, or `docs/document_schema.md`, whose ownership table still lists five tools and neither block.

### §1b — ✅ ADDRESSED: as first landed, §1 silently dropped all text and bbox
`BLOCK_FIELD_OWNERS["lines"]["llm-enrich-digital"] = ["group_id"]` meant `merge_block()` filtered `text` and `bbox` out **with no warning** (`_complain()` only fires when the grant is `None`), and the result still **passed** `jsonschema.validate()`, because `lines[]` requires only `page`+`line`. It surfaced three stages later as `json_to_md`'s `ValueError("nothing to render")`. Also: `lines[].bbox` had been granted to `nlp-enrich` and not to any originator, so the PDF adapter — whose whole point is exact coordinates — could not write the field that carries them. Both grants corrected; `bbox` is now deliberately granted to two writers who can never meet on one document, enforced rather than assumed.

### §1c — ✅ IMPLEMENTED: `group_id` was inert
`json_to_md._rows_from_lines` built `{page_num, line_num, text}` + optional `bbox` and dropped everything else, so the paragraph fidelity §1 bought never reached the model — while the canonical schema's `group_id` description asserted a CONSUMER CONTRACT and named `rows_to_layout_markdown()` as the implementing function, which had no group tracking in it. A false normative cross-reference in a file `para-drift` copies byte-identically into five repos. **Now actually fixed**: `group_id` is carried through and a boundary renders as a blank line, with a test pinning both the boundary and that output is byte-identical when no row carries the field. Three more consumer-side defects in the same path were fixed with it — non-numeric page labels were silently dropped and then misdiagnosed as "nothing to render"; `DOC_META` hardcoded `px` so every PDF page in POINTS was mislabelled (and `pdf_to_md.py` said `pt` for the same document); and with no `needs_ocr_reason` field every digital-born page rendered "no extractable text layer", which is false by definition for a document that has one. `tables` rendering is the remainder of PR 5.5 — deliberately not stubbed, and now expressible because `cells[].group_id` gives the join a key it did not have.
