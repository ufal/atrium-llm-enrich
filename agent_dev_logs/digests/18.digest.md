## 🎯 Goal
* Build an explicit converter (`api_util/digital_to_json.py`) that ingests digital-born `.pdf` and `.docx` files, extracts their structural and spatial layout formatting, and outputs them directly into the strict `atrium_document.schema.json` format for seamless LLM workflow integration.

## 🧵 Thread trail
* **2026-08-02** — Issue opened to bridge the visual layout cue taxonomy developed in Issue #10 with the new ecosystem-wide JSON standard.
* **2026-08-02** — Architectural review concluded that rewriting the old PDF/DOCX→Markdown scripts is a trap. The new flow must bypass Markdown entirely: `PDF/DOCX → Common Internal Python Model → canonical atrium_document.schema.json`.
* **2026-08-02** — Fidelity rules established: PDF provides the strongest spatial truth (strict bounding boxes, coordinates), while DOCX provides structural truth (paragraphs, runs, headings). DOCX adapters must not fabricate spatial bounding boxes if they rely on renderer-specific pagination.
* **2026-08-02** — Tool stack finalized: Docling as the primary foundation for structure, PyMuPDF for PDF geometry enrichment, and python-docx/docx2python as a DOCX fallback. Routing logic detects digital-born documents prior to sending anything to OCR.
* **2026-08-03** — Repo check against the `test` branch: Phase 0 prototyping (`test_docling.py`, `test_pymupdf.py`, `test_ooxml.py`) already exists under a new `digital_born/` directory, and `test_docling.py` has been run against `sample.pdf` — `digital_born/sample.pdf_docling_ir.json` (197KB) is real Docling output, not a stub. None of this is reflected in the DEVLOG or in this digest before now.
* **2026-08-03** — Same branch check: the legacy `api_util/pdf_to_md.py`, `api_util/docx_to_md.py`, and `api_util/doc_to_visual_md.py` (landed 2026-07-22) have been relocated into `digital_born/` alongside the prototyping scripts. `tests/test_pdf_to_md.py`, `tests/test_docx_to_md.py`, and `tests/test_doc_to_visual_md.py` still import them from `api_util`, so all three test modules currently fail at collection. `requirements_docmd.txt` also still documents the old `pdfplumber`/`pytesseract` stack and points at the now-stale `api_util/*` paths in its header comment; the new Docling/PyMuPDF/docx2python stack isn't declared as a dependency anywhere yet.
* **2026-08-03** — Schema reality check: `atrium_document.schema.json` has no paragraph/text-block grouping node. `pages` is a flat array of page metadata, `lines` is a flat array of line records (`page` + `line` index + `bbox`), `content` is doc-level reading-order text — there's no intermediate block layer. Separately, "block" is already the established term in this codebase for the schema's top-level field-owned sections (`BLOCK_FIELD_OWNERS`, `set_block()`/`merge_block()` from Issue #13), so the plan's mapping-table row "Text block → `block`" both collides with existing terminology and doesn't correspond to any real schema node.

## 🧭 The answer in one picture
* **Separate extraction, unified serialization.** We do not build PDF→JSON and DOCX→JSON separately. We build a `PDF Adapter` (Docling + PyMuPDF) and a `DOCX Adapter` (Docling + OOXML fallback) → `Normalized DigitalDocument (Internal Model)` → `AtriumDocument Serializer` → `Schema Validation` → `LLM Enrichment`.
* **Validation is a runtime gatekeeper.** If the extracted document fails validation against `atrium_document.schema.json`, the script fails loudly and refuses to emit a `doc.json`. Malformed data never reaches the LLM module.
* **Semantic vocabulary over raw HTML comments.** Legacy Issue #10 HTML cues (`<!-- PAGE_BREAK -->`, `<!-- BBOX -->`) are semantically mapped directly to JSON nodes (e.g., `page boundary`, `bbox` field) rather than blindly copied over.

## 🛠️ Landed
* **Architectural Contract** — ✅ The four-layer extraction strategy (Extraction → Normalization → Serialization → Validation) is locked in.
* **Tool Stack (decision)** — ✅ Docling selected as the primary abstraction layer, paired with PyMuPDF for geometric precision.
* **Phase 0 Prototyping (code, unreleased)** — ✅ but ⚠️ `digital_born/test_docling.py`, `test_pymupdf.py`, `test_ooxml.py` exist and have actually been exercised against `sample.pdf` / `sample.docx`, producing real Docling IR output. None of it is wired into the package, no requirements file declares the new deps, and it isn't mentioned in the DEVLOG.

Needs a decision: restore the old modules to `api_util/` until PR 7 (Migration) actually lands, or update the three test modules' imports to point at `digital_born/` as an interim location.
* **Stale requirements** — `requirements_docmd.txt` header comment and dependency list still describe the pre-migration `api_util/*` layout and the `pdfplumber`/`pytesseract` stack. Needs updating regardless of where the interim code lives, and the new Docling/PyMuPDF/docx2python stack needs to be declared somewhere before Phase 0 work is considered real infrastructure rather than scratch scripts.
