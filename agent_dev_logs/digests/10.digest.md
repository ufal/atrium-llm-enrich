## 🎯 Goal
Turn input **PDFs (curve-only / scanned / digital-born)** and **DOCX** into the repo's LLM-friendly
targets — since the 2026-07-21 comments, specifically into **visually-rich Markdown**: page borders
and layout cues recorded as HTML comments inside page-sectioned `.md`, so the LLM keeps layout
signal a plain-text dump would lose.

## 🛠️ What landed (`456ebb2`)
- **`api_util/layout_md.py`** — dependency-free **cue vocabulary**: pure emitters returning the
  taxonomy's exact strings + a `CUE_SCHEMA` catalogue ("the list of all possible visual layout
  pieces", single-sourced and testable).
- **`api_util/docx_to_md.py`** (python-docx, MIT) — styles→headings, emphasis + explicit FONT/STYLE
  cues, alignment, tables, headers/footers + margins, page breaks → `## Page N`, images, footnotes.
- **`api_util/pdf_to_md.py`** (pdfplumber, MIT) — per-page `DOC_META`, block `BBOX`+`FONT` (blocks
  split on gaps *and* font-size change), tables, **decode-sanity check** → text-less/garbled pages
  emit `NEEDS_OCR` instead of fabricated text.
- **`api_util/doc_to_visual_md.py`** — dispatcher + CLI: pre-convert, land the `.md` in `INPUT_DIR`,
  run the pipeline unchanged (HTML-comment cues pass through as inert text).
- Optional `requirements_docmd.txt`; 4 hermetic test modules.

## 🛠️ What landed (plan §7, 2026-07-22 — second pass)
- **Unified schema:** `xml_to_md.py --format layout` renders TEITOK/ALTO to the *same* annotated MD
  (DOC_META/BBOX/PAGE_BREAK/figure cues) from their coordinates — annotated MD is now the one diet
  across PDF, DOCX, and TEITOK/ALTO. Default `markdown`/`text` output byte-identical.
- **OCR (opt-in):** `pdf_to_md.py --ocr` renders text-less pages (pypdfium2) and transcribes them
  with Tesseract `ces` (`pytesseract`), tagged `<!-- OCR: engine=tesseract, lang=ces -->`; graceful
  fallback to `NEEDS_OCR` when the binary is absent. Default behaviour unchanged.
- **Citations:** the document schema returns an optional `page`; `run_document_level` surfaces it →
  `[Source: <doc_id>, Page N]` (issue #11 §3.3).
- **Auto-convert:** `llm_client_shared.prepare_document_input()` converts `.pdf`/`.docx` to a cached
  `.md`, wired into the openrouter/ollama clients (both gain `--ocr`). Suite **268 passed, 3 skipped**.

## 🧭 Research findings that still steer the rest (plan §1–§5)
- **Three PDF classes → two paths** via a cheap font+char+image census; **curves and scans are the
  same OCR path** (`curves.pdf` extracted 0 chars; Tesseract `ces` recovered the text).
- **4th class "extracts but garbled"** (no `/ToUnicode` → `sondě→sondI`) — now guarded by the
  converter's decode-sanity check; the valid-but-wrong-diacritics case needs a dictionary/LM
  hit-rate and rides with the OCR follow-up.
- **Recommended tools (permissive-first):** pdfplumber (landed) / PERO-OCR + Tesseract `ces` (OCR
  path, pending) / pandoc·mammoth (DOCX alternatives; python-docx landed) / Docling·MinerU (complex
  layouts — evaluate in #22). License traps: Marker (GPL + model revenue cap), PyMuPDF (AGPL),
  MinerU (custom), **flexiconv (GPL-3.0-or-later, declared in `pyproject.toml` only — policy decision)**.

## ⏳ Open / next
- **OCR tool selection** — the Tesseract `ces` path is live (opt-in); benchmark it against **PERO-OCR**
  (Czech-tuned) under hub #22 and wire the winner per quality tier at the same seam.
- **flexiconv licence** — declared GPL-3.0-or-later; recorded as a conditional `para_config.txt`
  component (`f62921c`). Decided for the services on 2026-09-24 (atrium-nlp-enrich #38): no service image
  bundles flexiconv; conversion stays a CLI step (nlp-enrich `api_flexiconv.sh`) and services accept its
  `.teitok.xml` output. Still open: the policy for CLI production runs. Nothing in this repo calls
  `log_component("flexiconv")`, so the `para_config.txt` row never reaches a run's licence; either log it where a
  conversion happens or mark the row as reader-only.
- ✅ (`f62921c`, on `test`) **flexiconv output is readable** — flexiconv's TEITOK has no `<s>` in any format; the
  canonical `api_util/teitok_read.py` from nlp-enrich (rows from `<lb/>` lines or text blocks when there
  is no `<s>`) and `api_util/flexiconv_convert.py` (real `flexiconv.api.run_convert` API,
  `--no-auto-install` CLI fallback) are re-vendored verbatim, pinned by
  `tests/test_vendored_teitok_parity.py`; `xml_to_md.py`'s layout reader uses the same helpers. See
  `atrium-nlp-enrich/agent_dev_logs/plans/10.plan.md` and `…/plans/teitok_conformance_plan.md` (Stage 5).
- ✅ **README section** — the converter is documented (README "Visually-Rich Document Input", flexiconv notes at
  `README.md:67-74`).
- ✅ **A `.teitok.xml` as line-level input enriched zero lines** (round 4, 2026-09-24): `read_input_rows()` gave
  every TEITOK row `quality_score 0.0` and the line filter turned anything below 0.40 into "Trash"; `stub_llm`
  patched the filter out, so no test noticed; a CSV without `quality_score` was hit the same way; the GPU path
  called `_should_process_line` with 6 of its 7 arguments. **Fixed 2026-09-24** (not yet on `test`):
  `llm_client_shared.row_quality()` / `llm_utils._row_quality()` return None for a missing score, the filters
  skip the quality bands for it, both GPU call sites pass it, and `stub_llm` replaces only `make_chat_fn`
  (947 tests pass). Details: [`13.plan.md`](../plans/13.plan.md) P5, [`../plans/10.plan.md`](../plans/10.plan.md) §8.
- ❓ **Which route to Markdown?** (stranak, 2026-09-23: a) markitdown, b) flexiconv, c) the custom
  converters). A draft answer from the code and the §5 measurements — the decision and the reply are the user's:
  - The repo already answered the upstream question in [#18](https://github.com/ufal/atrium-llm-enrich/issues/18)
    (2026-08-02): the `atrium_document` JSON is the intermediate format and Markdown is only the *view* the LLM
    reads, rendered by `api_util/json_to_md.py` / `xml_to_md.py --format layout` through one cue vocabulary
    (`layout_md.CUE_SCHEMA`); `digital_to_json.py` extracts with pdfplumber + python-docx (both MIT).
  - **a) markitdown** (MIT, v0.1.6 measured in §5): flawless on DOCX, but on `digital.pdf` headings were lost and
    the table flattened; it keeps no coordinates, page borders or font cues and does no OCR, so it cannot produce
    the cue taxonomy the issue asked for (2026-07-21).
  - **b) flexiconv** writes no Markdown: its v0.3.10 outputs are `teitok`, `tei`, `html`, `txt`, `docx`, `hocr`,
    `xpdf`, `rtf`, `conllu`, … (`flexiconv/cli.py`; `io/md.py` only reads). Its place is the TEITOK plane:
    nlp-enrich annotates its output ([atrium-nlp-enrich#38](https://github.com/ufal/atrium-nlp-enrich/issues/38)),
    this repo reads it and renders it to the same Markdown with `xml_to_md.py`. GPL-3.0-or-later, so a CLI step.
  - **c) the custom code**: the only option that emits the cues, the decode-sanity check (`sondě→sondI`) and the
    opt-in OCR. The maintained part is small because parsing is the libraries' — the cue layer
    (`layout_md.py`, 295 lines) and the adapters; the older `docx_to_md.py`/`pdf_to_md.py` are superseded by
    #18's `digital_to_json.py` + `json_to_md.py`.
  - Suggested reply: c) as #18 built it (JSON first, one Markdown renderer); b) for documents that go to TEITOK
    and NLP; a) not adopted — at most a fallback for DOCX/HTML where the cues do not matter.
- **Format/tool bake-off** — feed converter outputs through the #22 harness
  (`sample_stratify.py` + `eval_metrics.py` + `bench_compare.py`); the input-format decision is
  tracked in issue #11 ([`11.plan.md`](../plans/11.plan.md)).
