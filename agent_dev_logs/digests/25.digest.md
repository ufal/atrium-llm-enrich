## 🔎 What the issue establishes
- **Transport we already run:** PDF → `pdf2image` at `--dpi` (300) → Ollama vision chat → Markdown with page headers;
  this repo has `ollama_client.py`.
- **Four prompt/sampling profiles** (`standard`, `qwen38`, `glm`, `firered`) — prompt engineering for OCR, e.g. no
  invented Markdown emphasis on typewritten text, `[unreadable]` spans, one paragraph per physical line. Default
  model `qwen3.5:9b`; `glm` needs an Ollama server ≥ 0.9.0. Previous-page context is on for two modes (worth an
  ablation: continuation vs. carried-over hallucination).
- **What it does not give:** no geometry (no boxes, ALTO or PAGE XML), so it could only be a *text-plane* engine —
  it cannot fill `lines[].bbox`, feed the translator's ALTO reconstruction or give TEITOK boxes; no paradata;
  `requires-python >= 3.12` (we run 3.11), `PyPDF2` and `pdf2image`/Poppler (we use `pypdfium2`). Wrapping it at the
  `pdf_to_md.py` seam avoids importing the package.
- **Seam, named up front** (as `plans/24.plan.md` §B asks): #10's render+OCR path, beside Tesseract `ces` (landed,
  `pdf_to_md.py --ocr`) and PERO-OCR; the hub #22 VLM tier is a free follow-on.

## 🧭 How it fits (2026-09-24)
- #10's answer (5813071038) leaves the OCR engine to the #22 / #24 / #25 benchmark; the candidates at this seam are
  Tesseract `ces`, PERO-OCR, olmOCR (#24) and archivatorium. None has been scored.
- The `NEEDS_OCR` hand-off matters more than the engine for the record: by `ORIGIN_ORIGINATORS`, OCR output belongs
  to alto-postprocess (`ocr:`/`vlm:` origins), so a VLM transcription that should enter the positional plane needs an
  origin such as `vlm:archivatorium-<mode>` and a route through that originator — without boxes.
- `pdf_to_md.py` has `--ocr`, `--ocr-lang`, `--ocr-dpi`; there is no `--ocr-engine` switch yet. The `curves.pdf` /
  `scan.pdf` files the issue names were #10's 2026-07-19 research inputs and are not in the repository.

## ⏳ Open
